## 1. プロダクト概要

**日々の節約・支出管理・貯金を、街づくりの楽しさに変換する放置型育成ゲーム。**

- プレイヤーは現実の自由予算・購入・貯金を記録する。
- 街は内部経済によって **自律的に発展** する（操作を続ける義務はない）。
- **貯金額（債券 ＋ 都市に使った金貨＝現実で使わなかったお金）が技術Lvを上げ**、新しい建物や技術が解放される。
- ゲームの目的は街の最大化ではなく、**現実の貯金目標を達成すること**。目標達成が街のエンディングになり、成長の歴史がタイムラプスとして残る。

> 初期に街を設計する。日々の生活で技術を進める。街は時間とともに自ら発展する。

### 1.1 設計原則

1. 現実の金銭管理とゲーム内経済を明確に区別する（ゲーム内通貨は換金不可、積立は現実の預金の証明ではない）。
2. お金を多く使うことより、節約と継続を有利にする（記録報酬は金額に比例しない）。
3. 記録を忘れたりログインしなかったりしても不当に損をしない（放置で成長する）。
4. 予算超過・貯金の減少・資源不足で、建設済みの街を破壊しない。
5. 現実の支出を隠すことが有利にならない。
6. 1つの目標達成ごとに1つの街の物語が完結する。

### 1.2 プレイサイクルとフェーズ

| フェーズ | 内容 | プレイヤーの主な行動 |
|---|---|---|
| Phase 1 初期開拓（初回10〜20分） | 初期建物・土地用途・開発方針を決める | 建設・配置・用途指定 |
| Phase 2 自律発展 | 住民増加、自動増築・アップグレード、技術による進化 | 記録・金貨回収・任意の介入 |
| Phase 3 都市成熟 | 技術Lvで都市の姿が変わり、目標達成でシーズン終了 | 記録・観察 |

## 2. 用語・パラメータ

### 2.1 現実側（メタ）パラメータ

| パラメータ | 定義 | 更新方法 |
|---|---|---|
| 月間自由予算 B | 固定費・予定貯金を除いた自由に使える額 | 設定 |
| 月間サブスク額 S | 契約中サブスクの月額換算合計（年額は ÷12） | サブスク管理 |
| 貯金目標額 | 今シーズンで追加で貯める額（預金残高そのものはリセットしない） | シーズン作成時 |
| 収入日・収入期間 | 毎月の収入が入る日（1〜31、なければ1日）。収入日から翌月の収入日の前日までを1期間とし、採掘・C・精算の「月」に使う | 設定 |
| 月の収入 | 収入期間ごとの収入。雛形は B と通貨配分設定。差分だけを追加で配当・解消する | 収支記録で記録（未記録の期間は雛形で配当） |
| 貯金額 | 債券 ＋ 都市に使った金貨の累計（シーズンごと） | 自動 |
| 貯金最高到達額 | シーズン内の貯金額の最高値（技術Lvの根拠） | 自動 |
| 貯金管理の純増額 | シーズン内の 貯金追加 − 貯金引出（別口座への出し入れ。判定には使わない） | 収支記録で記録（1日3回まで） |
| 月間購入額 | その月の購入記録の合計 | 収支記録で記録 |
| 目標達成率 | max(0, 貯金額) ÷ 目標額 × 100 | 自動 |
| M（月に使えるお金） | 月間自由予算 B。債券の上限（3M）と倍率の基準 | 設定 |
| 債券化率 r | 採掘のうち債券に回す割合（0〜100%、10%刻み） | 配当資金 |
| 月の通貨発生額 C | その月にユーザ通貨が発生する額の合計（全通貨・全ルール）。採掘から差し引く | 通貨の定義から自動 |

### 2.2 ゲーム内通貨

| 通貨 | 獲得 | 用途 |
|---|---|---|
| 金貨 G | 銀行からの時間配当 | 資源・都市資金への交換（高効率。おまかせ可）、像への積立、銀貨・債券への交換、購入の精算 |
| 銀貨 S | 購入記録・貯金記録・金貨からの交換 | 資源・都市資金への交換（低効率。おまかせ可）、手動操作の手数料、債券を使ったときの手数料 |
| 債券 | 採掘の債券化・金貨からの交換・ユーザ通貨の余り | 購入の精算で足りない分の肩代わり（マイナス可）。持っているほど時間発展が速い。債券に入った分のうち0以上・上限以内の分は、同じ量の金貨と同じ資源も街に入る |
| ユーザ通貨 | 定義した発生ルール（毎分・周期・カレンダー指定日） | ジャンルが一致する購入の精算、債券への交換 |
| 都市資金 | 税収・商業・産業・金貨・銀貨からの交換 | 自動建設・自動アップグレード・自動進化 |

交換ルール：G→S は 1:1、G・ユーザ通貨→債券 は 1:1（無料。採掘・余りの債券化も含め、債券が 0〜3M の範囲に入る分は、同じ量の金貨をおまかせ交換した資源も街に入る）、S→G・S→債券・債券→他の通貨 不可、通常資源→通貨 不可。G→都市資金 は資源と同じ扱い（1G あたり 10 × Lvボーナス、手数料 5S、都市に使った金貨（貯金額）に加える。おまかせ・債券化の資源にも都市資金の不足分が入る）、S→都市資金 も資源と同じ扱い（1S あたり 1 × Lvボーナス、手数料 5S、貯金額には加えない）、都市資金→通貨 不可。マイナスになり得るのは債券だけ。
資源交換の基準価値は「1S ＝ 1G の 1/10」。

### 2.3 通常リソース（統合後）

| 種類 | 区分 | 役割 |
|---|---|---|
| 木材・石材 | 備蓄 | 建築資材 |

## 3. 特殊施設

### 3.1 銀行
- 目標・純増額・達成率を表示。達成率でレベルが決まる（0–19% Lv1 / 20% Lv2 / 40% Lv3 / 60% Lv4 / 80% Lv5 / 100% 完成）。
- レベルに応じて金貨・銀貨の資源交換効率ボーナス（+0/5/10/15/20/30%）。
- 達成率が下がるとレベルは再計算される。建物は消滅しない。技術Lvとは独立。
- 金貨の配当（3.2）と記録の報酬（3.3）も銀行の役割。以前の金鉱・銀鉱の建物は地図に置かず、既存の街からは読み込み時に取り除く（敷地は最初の土地用途に戻す）。未受取の配当は銀行の前の金貨の山で表す。
- 銀行のレベルは 銀行Lv（達成率）・配当Lv（3.2）・記録Lv（3.3）の3つで、交換効率のボーナスは足し合わせる。

### 3.2 金貨の配当（旧：金鉱）
- 採掘は月の収入の配当。毎分の採掘量 ＝ max(0, B − S − C) ÷ その収入期間の分数（月の収入を記録した期間は、雛形との差分の振り分け・減らしが加わる）。1分単位で採掘し、端数は内部で固定小数点（1G＝10⁶単位）で保持。回収できるのは整数部分。
- 月の境界・サブスクと毎分ルールの開始/終了時刻で採掘速度を区切って計算する（ユーザーのタイムゾーン基準）。
- 採掘のうち債券化率 r を債券へ直接入れる（上限 3M で停止）。債券がマイナスの間は max(r, 20%) を強制的に回す。債券化した分も配当Lvの累計に含める。
- タップで回収。複数端末から同じ金貨を二重回収できない。
- 購入の精算順：①像の積立金貨（紐付けた購入のみ） → ②ジャンルが一致するユーザ通貨（期限の近い順） → ③未回収金貨 → ④所持金貨 → ⑤債券（マイナス可）＋銀貨の手数料（使った債券の10%、上限50S。銀貨の不足分は債券から）。金貨・銀貨・ユーザ通貨はマイナスにしない。債券から払った額は月ごとに記録する（`MonthlyOverspend`）。過去の建物や資源は没収しない。
- 購入ごとに支払いの内訳を保存し、減額・削除は逆順（債券 → 所持金貨 → ユーザ通貨 → 像の積立金貨）で払い戻す。手数料は債券の支払い合計から計算し直す。
- 当月以外の日付の購入は家計履歴にのみ反映し、精算しない（締めた月を蒸し返さない）。
- レベルは累計回収金貨で決まり（0 / 5,000 / 15,000 / 40,000 / 80,000 / 150,000 G）、金貨の交換効率が上がる（+0〜20%）。採掘量は増えない。

### 3.3 収支記録（旧：銀鉱）
- 記録は **収入・支出・誤差調整** の3種類と、貯金管理（[record-input-redesign.md](record-input-redesign.md)）。
  - 収入：月の収入（未記録の期間を雛形で並べ、保存ボタンひとつ・一括保存。＋差分は振り分け、−差分は当期の未配当分 → 債券）、臨時の収入（全額を振り分け。初期値は即時貯蓄＝債券 → おまかせ交換）。
  - 支出：普通の支出（金額・日付・名称は必須、ジャンル・メモ任意）、サブスクの支払い・ほしい物の購入（設定から作ったベースを保存ボタンひとつで。ベースとの差は差分として解消）。
  - 誤差調整：手元のお金の推測（項目をチェックで足し引き、グラフつき、チェックは引き継ぐ）と実際の額の差を解消する。報酬なし。
  - 貯金管理：別口座への出し入れ（金額・日付・追加/引出・メモ）。1日3回まで。判定には使わない。
- 差分の解消：＋差分は債券へ上限まで（0〜上限の分は資源つき）、入りきらない分はおまかせ交換（手数料 5S、銀貨が足りなければなし）。−差分は全額を債券から（手数料：使った債券の10%、上限50S）。
- 登録した収支は金額だけ編集できる（変化分を差分として解消）。削除はなく、取り消しは金額0。
- 銀貨報酬：収入・支出 50S（月の収入は期間ごとに1回）、貯金管理 100S、誤差調整なし、1日 300S まで。金額に比例しない。同じ記録の報酬は1回だけ（編集・再送で再取得不可）。
- レベルは有効記録数で決まり（0/5/15/30/50/80件）、銀貨の交換効率が上がる（+0〜20%）。報酬量は増えない。
- 記録・金貨回収・G→S 交換は無料。

### 3.4 公園（サブスク）
- サブスク1件＝公園1つ。月額に応じて面積（装飾段階）が決まる。月額は採掘から差し引かれる。
- 解約すると閉園状態になる（取り壊しは任意）。
- 幸福度効果は逓減する（1つ目+6、以降は前の0.6倍、合計上限+15）。高額サブスクを契約しなくても街は十分発展する。
- 年額は ÷12 で月額換算。支払いは収支記録の「支出」に期間ごとに並び、登録額のまま保存すれば精算しない（二重計上の防止）。請求額との差は差分として解消する。

### 3.5 像（ほしい物）
- 登録すると像の建築計画が生成される。価格で 銅像（〜4,999円）/ 銀像（〜29,999円）/ 金像（30,000円〜）。
- 金貨を任意に分割投入。投入金貨は「積立済み金貨」として予約され、資源交換に使えない。購入前なら取消で返却。
- 進捗＝積立額÷価格。100%で資金準備完了。購入を記録すると完成し、積立金貨は価格の精算に充当する（二重計上なし）。価格より安く買えた分は＋差分、高かった分は−差分として解消する。
- 自動建設の対象外。像・公園は自動配置で撤去しない。

### 3.6 貯金額と欲しいもの貯金の表示

ホーム・銀行画面に2種類の貯金を並べて表示する。

| 表示 | 内容 | 増える時 | 減る時 |
|---|---|---|---|
| 貯金目標 | 貯金額 ＝ 都市に使った金貨（塗り）＋ 債券（斜線。マイナスなら減らし、全体は0未満にしない） | 金貨で資源・都市資金を得た時／債券の増加（交換・債券化・＋差分） | 債券を現実の支払いに使った時（精算・−差分） |
| 欲しいもの貯金 | 未購入のほしい物への積立金貨 ÷ その合計価格 | 像への積立 | 積立の取消・購入記録での充当 |

- 金貨はゲーム内で使っても現実のお金は出ていかないため、都市に使った額（1G＝1円）はそのまま貯金になる。銀貨払いの交換・金貨→銀貨の交換・像の積立は対象外。債券化の資源は債券で数えるので二重に数えない。
- 貯金額は技術Lv（最高到達額）・銀行Lv・目標到達（GOAL_REACHED）の判定と表示の両方に使う。貯金管理の記録では変わらない。
- 貯金額はシーズンごとにリセットする。

## 4. 街のシステム

### 4.1 建物の系統と段階

建物は「系統」に属し、技術Lvと発展Lvの **両方** を満たすと次の段階に進化できる（D-3）。

| 系統 | 段階（必要 技術Lv / 発展Lv） |
|---|---|
| 住宅 | 小屋(1/1) → 木造住宅(2/1) → レンガ住宅(3/2) → 集合住宅(4/3) → マンション(4/4) → 高層住宅(5/5) |
| 農業 | 畑(1/1) → 農場(2/1) → 機械化農場(3/2) → 大規模農場(4/3) → 自動農場(6/5) |
| 木材 | 木材加工所(1/1) |
| 石材 | 石材加工所(2/2) |
| 工業 | 工房(2/2) → 工場(3/2) → 大規模工場(4/4) → 自動化工場(6/5) |
| 商業 | 屋台(1/2) → 小売店(2/2) → 市場(3/3) → 商業施設(4/4) → 百貨店(5/5) |
| オフィス | オフィスビル(5/4) → 商業タワー(7/6) |
| 道路 | 未舗装道路(1/1) → 舗装道路(3/2) → 幹線道路(4/3) → 高度交通網(6/5) |
| 電力 | 発電所(3/2) → 高効率発電所(5/4) → 先進エネルギー施設(6/5) |
| 鉄道 | 鉄道駅(4/4) |
| 物流 | 物流センター(5/4) |
| 教育 | 学校(4/3) → 大学(5/4) → 研究所(6/5) |
| 医療 | 病院(4/3) |
| 文化 | 図書館(4/3) → 文化施設(5/4) |
| 未来 | 未来都市センター(7/6) |

- 建物Lv（1〜上限）は段階とは独立。上限は発展Lvで上がる（Lv1–3：3、Lv4：4、Lv5：5、Lv6：6）＝高密度化。
- 建物Lv倍率 ＝ 1 + 0.25 ×（Lv − 1）。
- 生産式：`実生産 = 基本生産 × 建物Lv倍率 × 技術倍率 × 労働充足率 × 電力充足率 × 物流効率`
- 技術倍率（技術Lv1〜7）：1.0 / 1.1 / 1.25 / 1.4 / 1.6 / 1.8 / 2.0。公共施設の **技術活用率**（70%〜100%）で倍率の上乗せ分の発揮度が決まる（D-1）。
- 食料と、電力需要0の基礎建物は電力なしで稼働する。

### 4.2 内部経済の循環

**人口 → 労働力 → 生産 → 供給 → 消費 → 都市資金 → 建設 → 人口増加**

- 人口増加速度 ＝ 基礎速度 × 住宅余裕率 × 雇用充足率 × 幸福度倍率 × 食料充足。
- 幸福度：食料・雇用・商業供給・公共施設・インフラ・公園（逓減）・工業の近接負荷から算出。
- 都市資金：住民税（人口×幸福度連動）＋商業売上（需要連動）＋工業収益。
- 資源は負にならない。不足時は生産効率と人口増加が落ちるだけで、建物は壊れない。
- 成長が指数的に暴走しないよう、人口増加は「一定値＋人口比例」とし、建物Lvアップの費用は Lv^1.5 で増える。目安：発展Lv2 が1日目、Lv4 が1週間前後、Lv6 が3週間前後、その後は高密度化（`scripts/balance.ts` で確認）。

### 4.3 自律型開発システム

一定間隔（10分）ごとに以下を実行する。

1. 資源・需要を評価する。
2. 優先順位（開発方針で並べ替え可能）に従って最初に実行可能な「必要事項」を目標にする。
   1. 食料・電力の不足解消
   2. 雇用不足の解消（仕事＜労働力）
   3. 住宅不足の解消（空きが15%未満）
   4. 物流の改善（物流効率＜90%）
   5. 生産効率の改善（技術進化・建物Lvアップ）
   6. 新産業への投資（未建設の解放済み系統）
   7. 余剰資金による景観改善
3. 目標に必要な資金・資材が足りなければ **貯める**（下位の項目に資金を流さない）。資材の生産手段がなければ先に資材施設を建てる。
4. 足りれば建設ジョブを作成する（建設時間あり）。同時ジョブ数に上限はない。1ティックに、方針の優先順で必要事項ごとに1件まで開始する（近いうちに払える上位の目標があれば、そこで止めて貯める）。
5. 建設禁止の建物・固定建物・公園・像・特殊施設には手を出さない。

技術Lvが上がっても既存建物は一瞬で置き換わらず、資金と時間を使って **1棟ずつ** 進化する。

開発計画は**計画列**として無限に続く：上の優先順の候補のあとに、解放済みの新築のうち最も高いものと同じコストの**拡張計画**が並ぶ（拡張計画は着工しない備蓄目標）。在庫を計画列の先頭から割り当てて最初に足りなくなった計画の不足分（木材・石材）と、食料の24時間分の不足分を**必要資源**とし、おまかせ交換・債券化の資源の割合に使う（[needs-based-exchange.md](needs-based-exchange.md) §4）。

### 4.4 自動建設と手動建設

| 項目 | 自動 | 手動 |
|---|---|---|
| 支払い | 資材＋都市資金 | 資材＋銀貨手数料 |
| 建物選択・配置 | 需要と開発方針・土地用途に従う | 自由 |
| 実行タイミング | 放置中も進行 | 操作時 |
| 対象 | 解放済み建物 | 解放済み建物 |
| 加速 | — | 銀貨で即時完了 |

手動操作と銀貨手数料：建設 10＋5×段階 S、アップグレード 10＋5×Lv S、移動 5S、資源交換 5S、即時完了 残り10分ごとに 2S。
手動で触った建物は自動配置変更の対象外になる。

### 4.5 発展度

- 時間発展 ＝ 経過時間 × 2pt/時 × 都市稼働係数（100% / 不足あり70% / 深刻30%、下限30%）× 債券倍率 k。
- 債券倍率 k ＝ 債券 ≤ 0 なら 1.0、それ以外は min(1.5, 1 + 債券 ÷ 6M)。建設時間・人口増加・建設完了などの発展ptには掛けない。マイナスでも1.0より下げない。
- 建設完了 +3、Lvアップ +1、段階進化 +4、人口の最高記録が25人増えるごとに +1。
- 同じ建物の建設・撤去を繰り返しても、一度計上した実績（建物ID×段階、建物ID×Lv）は重複計上しない。
- 発展Lv：Lv1 0 / Lv2 50 / Lv3 150 / Lv4 350 / Lv5 700 / Lv6 1,200 pt（集落→村→町→地方都市→大都市→巨大都市）。

### 4.6 技術Lv

| 技術Lv | 貯金額の最高到達額 | 解放内容 |
|---|---:|---|
| 1 | 0円 | 集落・農業 |
| 2 | 5,000円 | 基本産業・建物の自動増築 |
| 3 | 15,000円 | 工業化・発電・工場 |
| 4 | 30,000円 | 教育・研究・都市交通 |
| 5 | 60,000円 | 高度商業・オフィス・高層建築 |
| 6 | 100,000円 | 自動化産業・先進インフラ |
| 7 | 200,000円 | 未来都市・先端技術 |

- 発展度・通貨・時間では上がらない。購入記録でも上がらない。
- 技術解放で発展ポイントを直接付与しない。
- 貯金目標が小さければ全技術を解放せずにシーズン完了できる。

### 4.7 マップと土地用途

- 土地用途：住宅・商業・工業・農業・公共・特殊・未指定。初期は標準的な用途配置を提案し、プレイヤーが塗り替えられる。
- マップ（[map-layout-redesign.md](map-layout-redesign.md)）：銀行の中心を原点にした大きさを仮定しないマップ。初期は中心の 10×10 で、資源を使って 5×5 の区画ごとに開拓する（開拓できる区画数の上限は発展Lvで決まる）。建物の大きさは道路・像が 1×1、銀行と高額なサブスクの公園が 3×3、それ以外が 2×2。道路以外の建物は、銀行まで道路でつながった道路に接すること。
- 自動配置：用途が一致する土地 → 未指定の土地の順。同用途の隣接・道路の隣接を加点、住宅と工業の隣接を減点。

### 4.8 放置計算

- サーバーで常時計算しない。アクセス・記録・建物操作・交換・サブスク変更の時に、最終計算時刻から現在まで再計算する。
- 10分刻みの **絶対時刻に揃えたティック** で進める。いつアクセスしても同じ経過時間なら同じ結果になり（決定的）、同じ時間を二重計上しない。
- 債券倍率が街に効くため、ティックごとに「金貨の配当（債券化含む）→ ユーザ通貨の発生・期限 → 街の1ティック」を繰り返す。街はティック開始時の債券残高で倍率を決める。最後の端数は配当・ユーザ通貨だけ進める。
- 再訪時（前回から1時間以上）に「前回から◯時間」の変化（人口・建設・アップグレード・発展pt・都市資金）を表示し、変化したマスをハイライトする。

## 5. シーズン

- 状態：ACTIVE（進行中）→ GOAL_REACHED（達成率100%以上・確認待ち）→ COMPLETED（完了・アーカイブ）。同時に1つのみ。
- 達成率が100%に達すると達成画面を出し、「目標を完了する」で確定する（誤入力対策）。確認待ちの間も操作できる。引出で100%を下回れば ACTIVE に戻る。
- 完了時：街の状態を保存、イベント履歴を確定、建築・通貨操作を停止、タイムラプスを解放、アーカイブ。完了した街は再編集不可（タイムラプス再生のみ）。
- 新シーズン：街・資源・通貨（債券はマイナスも0に、ユーザ通貨の残高も0に）・施設Lv・像の進捗・貯金純増額・発展度・技術Lv・都市資金をリセット。アカウント・家計履歴・予算・サブスク・ほしい物（未購入分）・ユーザ通貨の定義・ジャンル・債券化率・過去のタイムラプスは引き継ぐ。金貨は新シーズン開始後の時間のみ配当する。

## 9. データ

### 9.1 テーブル（実装上の対応）

| 要件上のデータ | 実装 |
|---|---|
| users / user_settings | `User`（予算・タイムゾーンを含む）、`Session` |
| seasons / savings_goals | `Season`（目標額・状態・開始/達成/完了日時） |
| savings_transactions / purchases | `SavingsTransaction`（貯金管理） / `Purchase`（シーズンと独立した家計履歴、記録時のシーズンIDを保持。サブスクの支払いは `subscriptionId`・`periodKey`） |
| incomes | `Income`（月の収入・臨時の収入、振り分け）・`ScheduledGrant`（予約した振り分け） |
| 差分の解消 | `Resolution`（収入・支出・誤差調整ごと。金額の編集の前後も持つ） |
| 誤差調整 | `CashAdjustment`（チェック・各項目の額・推測・実際・誤差） |
| 貯金額・収入期間 | `Season.citySpentGold`・`Season.maxSavingsAmount`・`Season.mineWindows`・`mineCut`・`mineDividend`・`customCuts`、`User.incomeDay`・`incomeEras`・`estimateChecks` |
| subscriptions | `Subscription` |
| wish_items / wish_contributions | `WishItem`（元データ） / `WishContribution`（シーズン別の積立） |
| currency_ledger | `CurrencyLedger`（金貨・銀貨・積立金貨・債券・ユーザ通貨の増減を全件記録。ユーザ通貨は `currencyId` で区別） |
| 債券 | `Season.bond`（マイナス可）・`Season.mineBondFraction`、`User.bondMiningRate` |
| ジャンル | `Category`（`Purchase.categoryId`。`Purchase.category` は表示用の名前） |
| ユーザ定義通貨 | `CurrencyDef`（定義、ユーザー単位）・`CurrencyLot`（発生1回分、シーズン単位）・`CurrencyAccrual`（発生の進み具合） |
| 購入の支払い内訳 | `PurchasePayment`（払い戻しを逆順に行うため） |
| reward_claims | `RewardClaim`（記録ID単位で一意） |
| city_events / city_snapshots | `CityEvent` / `CitySnapshot`（開始時・完了時） |
| buildings, resource_balances, city_progress, technology_progress, city_treasury, city_policies, city_districts, auto_construction_jobs, city_simulation_state, city_demands | `CityState.state`（1シーズン1行のJSON。楽観ロックの `version` 付き） |
| building_production / building_consumption | 建物カタログ（コード上の定義）から算出 |
| （冪等性） | `IdempotencyKey`（同一操作の再送を検出） |

街の状態を1行にまとめるのは、放置計算で全建物を一括更新するためと、1ユーザーの操作を1トランザクションで直列化するため。

### 9.2 ルール
- 現実の金額は円の整数。配当の端数は 10⁻⁶G 単位の整数。
- 通貨の増減は台帳で管理。すべての記録に一意ID。報酬は記録IDで1回のみ。
- 同一ユーザーの操作はトランザクション内でユーザー単位のロックを取り直列化する。`Idempotency-Key` ヘッダーによる再送防止。
- 時間計算はサーバー時刻が基準（端末の時計変更は無効）。
- 完了したシーズンのゲーム履歴は変更不可。
