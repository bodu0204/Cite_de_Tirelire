# 街の描画 要件定義（Pocket City 型への作り直し）

作成日：2026-10-16
関係：[requirements.md](requirements.md) の FR-048、[応用案](city-idle-research.md) の A1・A2・A5〜A8・A11、[texture-management.md](texture-management.md)

## 1. 目的と方針

街を [Pocket City](https://apps.apple.com/app/id1330451888) のような描画にする。具体的には次の4点を目指す。

- **斜め見下ろしの2.5D（アイソメトリック）。** 建物に高さがあり、段階が上がるほど背が伸びて見た目で分かる。
- **広い街を指で動かして見る。** パンとズームで見回せる。マップの大きさを描画側で制限しない。
- **街が生きて見える。** 道を人や車が行き交い、煙や灯りが動く。
- **画像の質をそろえる。** すべての絵を同じ画風・パレット・光源・画素サイズで描く。

絵は PixelLab API で生成した PNG を使う。生成は開発時に1回だけ行い、選んだ PNG をリポジトリに入れて配信する。実行時に AI で絵を作る機能（FR-028 の像・公園の AI ドット絵）は、本書では扱わない。後から足せる形にだけしておく（§9）。

### 1.1 決めること（本書の前提）

| 項目 | 決定 | 理由 |
|---|---|---|
| 射影 | 2:1 のアイソメトリック（横2px進むごとに縦1px） | ドット絵の斜め線が一番きれいに出る標準の角度。PixelLab の isometric 系エンドポイントもこの形 |
| 基準タイル | 地面のひし形を 64×32px（2026-10-23 確定。M0 で 32×16 と比べ、32px では屋根の形や窓が潰れた） | 64px あれば窓・屋根・看板を描き分けられ、A1 の「段階の差が分からない」問題を解ける。PixelLab は 24px 以上で質が上がる |
| 描画エンジン | PixiJS（WebGL）。Canvas 2D から置き換える | マップを広げると、画面外の省略・地面の焼き付け・数百の人や車が必要になる。Pocket City も Canvas では性能が足りず WebGL に戻した（応用案 A11） |
| 回転 | しない（視点は1方向に固定） | 回転すると建物ごとに4方向の絵が要り、質をそろえる手間が4倍になる |
| 建物の大きさ | 今は全建物1マス。データには `footprint`（占めるマス数）を持たせておく | 将来の2×2建物（スタジアム等）に備える |

## 2. 範囲

### 2.1 含む

- 描画エンジンの置き換え（SCR-01 ホーム、像のプレビュー、目標達成、タイムラプス）
- カメラ（パン・ズーム・選択）
- マップサイズに依存しない描画（チャンク分割・画面外の省略）
- 地面・道路の接続・未開放区画・建物・工事・特殊施設・人と車・演出・昼夜
- PixelLab による素材生成パイプラインと品質基準

### 2.2 含まない

- **マップを広げるゲーム設計。** 今のマップは10×10固定です（`MAP_SIZE`、requirements.md 4.7 の区画解放、`layout.ts`・`init.ts`）。どの大きさまで、どの順に広げるか、シミュレーションの計算量をどうするかは別途決める。本書は「描画側は大きさを仮定しない」ことだけを要件にする。
- 実行時の AI 画像生成（FR-028）
- 視点の回転、3D 化

## 3. 描画の要件

### 3.1 座標と重なり順

| ID | 要件 |
|---|---|
| RND-01 | マップ座標 (x, y) から画面座標への変換は `sx = (x − y) × 32`、`sy = (x + y) × 16` を基本にする（基準タイル 64×32 の場合）。逆変換でタップ位置からマスを求める |
| RND-02 | 絵の基準点は「足元のひし形の中心」とする。絵の大きさが違っても、基準点を合わせれば地面にぴったり乗る |
| RND-03 | 建物・人・車・小物は、奥から手前へ（`x + y` の小さい順、同じなら `x` の小さい順）に描く。人や車は連続した位置で並べ替え、建物の陰に正しく隠れる |
| RND-04 | 描画層は下から「地面 → 用途の色・選択のひし形 → 影 → 建物・人・車（並べ替え済み） → 演出 → 困りごとアイコン（A3） → 夜の暗さと灯り → 選択した建物の輪郭」 |
| RND-05 | 建物の影は絵に焼き込まず、別の層に1色の半透明で描く。影が重なっても濃くならないようにする |

### 3.2 マップサイズに依存しない描画

| ID | 要件 |
|---|---|
| RND-10 | 描画コードは `MAP_SIZE` を参照しない。マップの範囲はサーバーから受け取るデータで決める |
| RND-11 | 地面は 16×16 マスのチャンクごとに1枚のテクスチャに焼き付ける。マスが変わった時は、そのチャンクだけ焼き直す |
| RND-12 | 画面外のチャンク・建物・人や車は描かない（カリング）。余白は1チャンク分 |
| RND-13 | 検証用に 128×128 マスのダミーマップを用意し、§7 の性能目標をこれで確かめる（実際の上限はゲーム設計で決める） |

### 3.3 カメラと操作

| ID | 要件 |
|---|---|
| CAM-01 | 1本指（マウスはドラッグ）でパンする。指を離した後は慣性で少し流れて止まる。マップの外へは出過ぎない |
| CAM-02 | ピンチ・ホイール・＋−ボタンでズームする。ボタンはドラッグできない人の代替を兼ねる（[WCAG 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)） |
| CAM-03 | **ズームは整数倍で止まる。** 1ドットを画面の1・2・3・4物理ピクセルに対応させる。ピンチ中は連続的に動き、指を離すと一番近い整数倍に吸い付く。ドットの太さが不ぞろいになるのを防ぐ（§5 の品質要件） |
| CAM-04 | カメラ位置は、その時の倍率で物理ピクセル単位に丸める（ドットのにじみ・ちらつきを防ぐ） |
| CAM-05 | タップでは、手前の建物の絵（不透明な画素）を先に判定し、当たらなければ地面のマスを選ぶ。背の高い建物は、上の方を触っても選べる |
| CAM-06 | 矢印キーで選択マスを動かす（今の操作を引き継ぐ）。カメラは選択マスを追う |
| CAM-07 | 最後に見ていた位置と倍率を端末に覚えておき、次に開いた時に戻す（読めなければ街の中心から始める） |
| CAM-08 | 一覧から地図の現場へ飛ぶ（応用案 B6）ためのAPI `focusTile(x, y)` を用意する。カメラがそのマスへ滑らかに移り、マスを点滅させる |
| CAM-09 | 像のプレビュー・目標達成・タイムラプスは、カメラを固定した表示モードで使う（タイムラプスは街全体が収まる倍率） |

### 3.4 表示するもの

今の [draw.ts](../src/components/city/draw.ts) が描いているものは、すべて新しい描画でも出す。

| ID | 対象 | 要件 |
|---|---|---|
| OBJ-01 | 地面 | 草を4種以上用意し、座標から決まる乱数で混ぜる（同じ街はいつも同じ見た目） |
| OBJ-02 | 未開放の区画 | 暗く塗るのではなく、林・岩・霧で覆う。次に開く区画には柵か看板を立てる（応用案 A8） |
| OBJ-03 | 道路 | 上下左右の隣接に合わせて、まっすぐ・曲がり角・T字・十字・行き止まりを描き分ける（応用案 A2）。4段階すべてで用意する |
| OBJ-04 | 建物 | 全系統・全段階（36種）に絵を用意する。**同じ系統の中で、段階が上がるほど背が高くなる**（応用案 A1） |
| OBJ-05 | 建物Lv | 段階ごとの絵は1枚で、Lvは共通の小物（屋上設備・看板・増築部分など）を重ねて示す。今の「下端の点」はやめる |
| OBJ-06 | 特殊施設 | 銀行（Lv1〜6、Lv6は完成）、金鉱、銀鉱、公園（段階0〜3と閉園）、像（銅・銀・金と、建設の5段階＋完成） |
| OBJ-07 | 工事 | 建設中は足場、改築中は覆いの絵を出す。進み具合のバーは絵ではなく描画側で描く |
| OBJ-08 | 用途の表示 | 用途の色をひし形で半透明に重ねる。色だけに頼らず、用途ごとの小さな記号も出す |
| OBJ-09 | 自動開発の対象外 | 今の赤い角印に代えて、ひし形の角に記号を出す |
| OBJ-10 | 選択・強調 | 選択マスはひし形の枠、選択した建物は輪郭を光らせる。強調（B6）は点滅させる |
| OBJ-11 | 人と車 | 道路の上を人と車が動く。数は人口・物流効率に比例させ、上限を設ける。位置はシード付き乱数で決め、再読み込みやタイムラプスでも同じ見た目にする（応用案 A5） |
| OBJ-12 | 動き | 煙突の煙、風車、噴水、トラクター、発電所などは、PNG のコマ送りで動かす |
| OBJ-13 | 演出 | 完成時の粒、進化時の光（応用案 A6）。困りごとアイコン（A3）と金貨の山（A4）を出す層も用意する |
| OBJ-14 | 昼夜 | 実際の時刻に合わせて、暗い色を乗算で重ね、窓の灯りを加算で足す。灯りは建物ごとの「発光マスク」で描く（応用案 A7） |

### 3.5 アニメーション

| ID | 要件 |
|---|---|
| ANI-01 | 450ms ごとの React 再描画をやめる。描画ループは PixiJS のティッカーで回し、React は盤面のデータが変わった時だけ描画側へ渡す |
| ANI-02 | コマ送りの速さは絵ごとに JSON で持つ（6〜12fps） |
| ANI-03 | `prefers-reduced-motion` の時は、人や車を止め、煙などの動きとカメラの慣性・移動の動きをなくす |

## 4. 素材の生成（PixelLab）

### 4.1 流れ

生成は開発者の手元で動かすスクリプト（`scripts/sprites/`）で行う。API キーは `.env` の `PIXELLAB_API_TOKEN` に置き、ブラウザには出さない。

1. **画風の基準を作る（最重要）。** マスターパレット（48〜64色）、光源、輪郭の付け方を決める。代表の5枚（木造住宅・市場・工場・舗装道路・草のタイル）を、候補を多めに出して選び、必要なら手で直す。以後の生成は、すべてこの5枚を画風の参照に使う。
2. **台帳を書く。** 絵1つにつき1行で、キー（例 `building/housing/2`）、使うエンドポイント、大きさ、プロンプト、参照画像、シードを書く（`scripts/sprites/manifest.json`）。
3. **候補を出す。** 1つの絵につき4つ以上の候補を出し、`art/candidates/<キー>/` に保存する。
4. **選ぶ。** 候補を並べた確認ページで1つを選ぶ。
5. **後処理する。** パレットへの割り当て、透明度の整理、余白の切り取り、基準点の設定（§4.3）。
6. **必要なら手で直す。** Aseprite などで直してよい。正本はプロンプトではなく、最終的な PNG とする（モデルが更新されると、同じシードでも同じ絵は出ないため）。
7. **アトラスにまとめる。** ビルド時に PNG をまとめて1〜数枚の画像と JSON にする。JSON は PixiJS の Spritesheet 形式にする。ファイル名には内容のハッシュを付ける。

### 4.2 エンドポイントの使い分け

API は v2（`https://api.pixellab.ai/v2`）を使う。生成は非同期なので、ジョブIDを `GET /background-jobs/{id}` で待つ。

| 素材 | エンドポイント | 使い方 |
|---|---|---|
| 建物・特殊施設 | `POST /generate-image-v2` | `style_image` に画風の基準を渡し、`target_palette` にマスターパレットを渡す。**1つ前の段階の絵を `reference_images` に入れる**と、系統の中で見た目がつながる。64px なら1回で16候補、128px なら4候補が出る |
| 建物（画風合わせの代替） | `POST /generate-with-style-v2` | 参照画像を最大4枚渡して画風を合わせる。`generate-image-v2` で画風がずれる時に使う |
| 地面・地形の境目 | `POST /create-tiles-pro` | `tile_type: "isometric"`、`tile_feature: "tileset"` で境目の16枚組を作る。**`tile_feature: "tileset"` と `style_images` は一緒に使えない**ので、画風は `target_palette` とプロンプトで合わせる（2026-10-23 確認） |
| 地面（草など） | `POST /create-tiles-pro` | `tile_feature` なしで、種類違いのタイルを1回で16枚作る（説明を「1). … 2). …」と番号付きにする）。`tile_view_angle: 30`（2:1 のひし形になる角度）、`tile_depth_ratio: 0.1`、`tile_flat_top_px: 2`、`outline_mode: "segmentation"`（輪郭なしで、つなぎ目が目立たない）。`generate-image-v2` ではひし形が枠いっぱいにならない |
| 道路 | `POST /create-tiles-pro` | `tile_type: "isometric"`、`tile_feature: "roads"` で、つながり方18通りの組を作る。4段階それぞれで作る。地面と同じ角度・輪郭の指定にする。**T字路は4通りのうち1通りしか出ない**ことがあり、左右反転で1通りは補えるが、残り2通り（北東西・北南西）は補えない（上下反転すると厚みと光が逆になる）。足りない分は追加で生成するか手で描く |
| 未開放区画の岩・林・柵 | `POST /create-isometric-tile` か `POST /map-objects` | `map-objects` は `background_image` で周りの地面に画風を合わせられる |
| 人・車 | `POST /create-8-direction-object`、`POST /animate-with-text-v3` | 斜め4方向だけ使う。歩く動きは4コマ |
| 煙・粒・光 | `POST /vfx` | 基準点付きのスプライトシートと JSON が返るので、そのまま取り込める |
| 建物の動き（風車など） | `POST /animate-with-text-v3` | `drift_threshold` でコマ間の色のちらつきを抑える |
| 夜の姿 | `POST /edit-images-v2` | 「同じ建物の夜、窓に灯り」で夜版を作り、昼版との差から発光マスクを取り出す。うまくいかない時は手で描く |
| 後処理 | `POST /reduce-colors` | `palette_image` にマスターパレットを渡す。アニメの全コマは1回でまとめて渡し、コマ間で色をそろえる |

### 4.3 後処理の自動チェック

アトラスにまとめる前に、スクリプトで次を確かめる。1つでも外れたらビルドを止める。

| ID | チェック |
|---|---|
| LINT-01 | catalog の全系統×全段階、全特殊施設、全道路パターンに絵がある（texture-management の「抜け漏れテスト」を引き継ぐ） |
| LINT-02 | 全画素の色がマスターパレットに含まれる |
| LINT-03 | 透明度が 0 か 255 のどちらか（影・演出の層は除く）。半透明のにじみがない |
| LINT-04 | 幅が基準タイルの幅（64px）の倍数で、基準点が足元のひし形の中心にある |
| LINT-05 | 1ドットが1画素である（2×2 などに拡大された生成結果が混ざっていない） |
| LINT-06 | アニメの全コマが同じ大きさで、同じ基準点を持つ |
| LINT-07 | 同じ系統の中で、段階が上がるほど絵の高さが同じか高くなる |

## 5. 画像の品質基準

自動チェック（§4.3）に加えて、確認ページ（§5.2）を人が見て合否を決める。

### 5.1 画風のルール

| ID | ルール |
|---|---|
| ART-01 | **画素の大きさをそろえる。** 生成した絵を拡大・縮小しない。必要な大きさで生成する |
| ART-02 | **光源は左上。** 建物の右側の面を暗くし、影は右下に落とす |
| ART-03 | **輪郭は「selective outline」（面の色に合わせた輪郭）でそろえる。** 黒一色の輪郭と混ぜない |
| ART-04 | 1枚の色数は32色以内。全体はマスターパレット（48〜64色）の中だけを使う |
| ART-05 | 系統ごとに識別色を決める（例：住宅は赤系の屋根、商業は青系の日よけ、工業は灰と黄）。段階が変わっても識別色は保つ |
| ART-06 | 段階の差は、高さ・屋根の形・輪郭で出す。同じ大きさで色だけ変える描き分けはしない |
| ART-07 | 文字は入れない（AI 生成の文字は崩れるため。看板は記号で表す） |
| ART-08 | 地面・道路のつなぎ目に段差や色のずれがない |

### 5.2 確認ページ

開発環境だけで開けるページを用意し、次を並べて見られるようにする。

- 系統ごとの全段階を横一列に並べる（等倍と2倍、昼と夜）
- 草の地面に建物を並べた街の見本（道路・人・車を含む）
- 生成の候補一覧と、選んだ絵の比較

合格の目安は次の3つ。

- 等倍（1ドット＝1物理ピクセル）で、同じ系統の段階を見分けられる
- 並べた時に、画風が浮いている絵がない
- 夜に、窓の灯りが建物の形に合っている

## 7. 性能・互換性

| ID | 要件 |
|---|---|
| NF-01 | iPhone 12・Pixel 6 相当の端末で、128×128 マスのダミーマップ、人と車300体を表示し、パン中に 60fps を目標、30fps を下限とする |
| NF-02 | 動きがない時は、アニメに必要な fps まで描画回数を下げる。タブが裏に回ったら止める |
| NF-03 | アトラスは1枚 2048×2048px 以内に分ける。画像の合計は 4MB 以内を目安にする |
| NF-04 | 画像は拡大時に補間しない（nearest）。ミップマップは使わない。アトラス内の絵の間に余白を入れて、隣の絵がにじまないようにする |
| NF-05 | 画面の解像度（devicePixelRatio）に合わせて Canvas の実サイズを決める |
| NF-06 | WebGL のコンテキストが失われたら作り直す。WebGL が使えない環境では、街の代わりに案内文と数値の情報を出す |
| NF-07 | Canvas には街の状態を要約した `aria-label` を付ける（今の仕様を引き継ぐ） |

## 8. 進め方

| 段階 | 内容 | 終わりの条件 |

生成の手順：

1. `npm run sprites -- balance` で残高を確かめる（クラウド環境では先頭に `NODE_USE_ENV_PROXY=1` を付ける。Node の fetch がプロキシを使うようにするため）
2. `npm run sprites -- --tw 64 --stage M0 --dry-run` で送る内容を確かめる（課金なし）
3. `npm run sprites -- --tw 64 --stage M0` で候補を作る。`--tw 32` でも作って比べる
4. `/dev/sprites` で候補を選ぶ。選んだ絵は `art/sprites/<tw>/<キー>.png` に入り、Git で管理する（候補の `art/candidates/` は入れない）

費用の目安：`generate-image-v2`・`create-tiles-pro` は、1回 10 generations（16〜256px。クレジット払いなら約 $0.09）。1回で出る候補は絵の長い辺で決まり、64px なら16枚、65〜84px なら9枚、86〜170px なら4枚。実際の消費は返答の `usage` で確かめる。

M0 で分かったこと（2026-10-23）：

- **生成は `status: completed` まで待つ。** 仕上げ中（`processing`）の返答にも途中の画像が入っている。
- **建物は `generate-image-v2` でよい。** 64px なら窓・扉・屋根窓まで描き分けられる。32px は屋根の形が潰れ、段階の差を出しにくい（64×32 を推す理由）。プロンプトで「土台なし」と書かないと、建物ごとに土や芝の板が付く。輪郭は黒になりやすい（ART-03 の selective outline は後処理か `style_image` で合わせる）。
- **地面と道路は `create-tiles-pro` で作る。** `generate-image-v2` の草や道路は、ひし形が枠いっぱいにならず（64px の枠に幅46px など）、並べると隙間が出る（ART-08）。道路は向きの指示にも従わない。`create-tiles-pro` は正確なタイルの形で作り、`tile_feature: "roads"` ならつながり方の規則（`tile_rules`。ビットは北1・東2・南4・西8で、このリポジトリの `roadMask` と同じ）も返す。
- **タイルは `scripts/sprites/import-tiles.ts` で取り込む。** 道路は `tile_rules` のつながり方でキーを付け、地面は選んだ番号を 0, 1, 2… にする。ひし形の先端より上に乗る切れ端は消し、基準点を画像から求めて `art/sprites/<tw>/anchors.json` に書く。
- **M1 で直すこと（§8.2 で対応済み）。** (1) 道路のタイルの草が地面の草より明るい。(2) 建物は黒い輪郭、地面と道路は輪郭なしで、ART-03 にそろっていない。(3) T字路が足りない。
- **描画を作り直す時は `app.destroy(true)` にしない。** PixiJS 全体で共有する資源まで解放し、同時に動く別の描画を壊す。
- **`create-tiles-pro` の画像は `backblaze.pixellab.ai` から配られる。** API の `api.pixellab.ai` とは別に、ネットワークの許可が要る。生成は済んでいれば `npm run sprites -- refetch <候補のフォルダ>` で追加の課金なしに取り直せる（各フォルダの `job.json` にジョブの ID を残している）。

生成の進め方：段階は前の段階の絵を `reference_images` に渡して順に作る（系統の見た目がつながる）。画風は木造住宅（`styleKey`）を `style_image` に渡してそろえる。候補を見て1枚選び、`npm run sprites`（生成）→ `scripts/sprites/finish.ts`（後処理して `art/sprites/64/` へ）の順。LINT-07 に外れる組み合わせ（前の段階より低い）は選び直す。

M1 の終わりの条件（今の描画でできたことが全部でき、LINT が全部通る）は満たした。ただし、今の描画にあった動き（煙・トラクター・車・銀行Lv6のきらめき・公園の噴水）は、計画どおり M2（OBJ-12 の建物の動き）で PNG のコマ送りとして入れ直す。生成の費用は M0〜M1 で約 920 generations。

残っている気になる点（M2 以降で直す）：

- 銀行Lv5 は、ドームの先端が3px 枠で切れている（4候補すべてが切れていた）。
- 背の高い建物の一部（自動化工場・先進エネルギー施設・百貨店など）は、横幅いっぱいに描かれていて、隣のマスの建物と重なって見えることがある。
- 公園・像・林は、絵に小さな地面の板（厚み）が付いている。マス全体を覆う絵なので、ほかの建物と並べても大きな違和感はない。

M1 で分かったこと：

- **背の高い絵（2タイル以上）は、枠いっぱいに描かれて上や横が切れやすい。** プロンプトに「屋根やアンテナまで枠に収め、上に少し透明な余白を残す」と書く。選ぶ時は、一番上の行に画素がないかを確かめる。
- **生成した建物は、足元が絵の一番下とは限らない（下に数px の余白が残る）。** 基準点は「不透明な画素の一番下＝足元のひし形の下の頂点」から求める（`build-atlas.ts`）。
- **アトラスの canvas から PixiJS のテクスチャを作る時は `Texture.from(canvas, true)`（内部の記憶を使わない）。** 使うと、作り直す前の描画が破棄したテクスチャを、新しい描画が受け取ってしまう。
