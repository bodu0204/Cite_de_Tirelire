## 1. まとめ

**よくできている点**：放置計算は決定的で、二重計上を防いでいる。発展ptの実績は最高記録を超えたときだけ数える（建て直しで稼げない）。人口は減らず、資源は負にならず、技術Lvは下がらない（設計原則4）。金貨→銀貨→資源が金貨→資源より有利にならないことをテストで保証している。記録の報酬は金額に比例せず、1日の上限がある（設計原則2）。`balance.ts` の前提では、発展Lvの目安（Lv2 が1日目、Lv4 が1週間前後、Lv6 が3週間前後）を満たしている。

**問題**：`balance.ts` の前提（40日で20万円、金貨は使わない）から外れると、自動開発が止まる・壊れる場面がある。とくに次の3つは、街が数か月にわたって動かなくなるか、技術Lvが上がったとたんに生産が止まる。貯金して技術Lvが上がると街が良くなる、というこのゲームの中心の体験を損なう。

## 2. 調べ方

### 2.1 シミュレーション

`scripts/balance-scenarios.ts`（今回追加。`balance.ts` を広げたもの）で、街のシミュレーション（`tick`）を日ごとに進めた。

- 採掘は B ÷ 30 を毎日（B＝60,000円）。貯金はその一定割合（SAVE）。
- 金貨の使い方：使わない（none）／その日の貯金分を毎日おまかせ交換と同じ資源にする（city）／債券に入れる（bond。資源は city と同じで、債券倍率 k もかかる）。
- 単純化：収入期間・サブスク・ユーザ通貨・購入の精算・手動操作は扱わない。施設Lvは貯金額・累計採掘・1日3件の記録から求める。
- 「fast」は `balance.ts` と同じ貯金スケジュール（1日目 5,000円 … 40日目までに計20万円。月15万円のペース）。「real」は月12,000円（B の2割）で、目標10万円に約250日かかる。

## 3. 重大な問題

<a id="gb-01"></a>
### GB-01 発電所がないまま電力を使う段階へ進化し、生産が止まる（重大）

**現象**（シナリオD）：技術Lv3（d38）になった翌日に、農場は機械化農場（電力2）、工房は工場（電力4）、小売店は市場（電力1）へ一斉に進化した。発電所は0棟のままで、電力の需要 467 に対して供給0。

| | d37（技術Lv2） | d38（技術Lv3） | d120（技術Lv4） |
|---|---:|---:|---:|
| 食料の生産（/時） | 151 | 0 | 0 |
| 電力（供給/需要） | 0/0 | 0/467 | 0/1,465 |
| 幸福度 | 74 | 56（目標値39） | 36 |
| 都市資金の収入のうち税以外（/時） | 656 | 281 | 0 |
| 農場 | 7 | 11 | 31 |

毎日おまかせ交換で食料も入るが、1日の終わりには在庫が0になる。シナリオG（産業優先）でも d10 に電力が0になり、d20 には食料も0になって、人口23のまま止まった。

**原因**

- 生産は `電力充足率` を掛けるので（[economy.ts](../src/game/city/economy.ts) `buildingOutput`）、電力0なら電力を使う建物の生産は0になる。
- `evolvePlans` と `buildPlanAt` は電力の余力を確かめない（[sim.ts](../src/game/city/sim.ts)）。食料が足りないときの候補は「農場の進化」が先頭で、進化すると電力がないので逆に生産が0になる。新築する農場も最上位の段階（電力が要る）なので、動かない農場が増えていく（7 → 31棟）。
- 発電所は工業地区に置く。シナリオD では技術Lv3 になったときに工業地区の空きがなく、開拓（同時に1件、費用は指数的に増える）を待つ間に、都市資金が進化に使われてしまう。開拓した区画は先に候補に出た農場の用途（農業地区）になり、発電所は最後まで建たなかった。

シナリオA で起きないのは、技術Lv3 が7日目と早く、工業地区がまだ空いていたため。現実的な貯金ペースでは、技術Lv3 の時点で土地が埋まっていることが多い。

**提案**

1. 電力を使う段階への進化・新築は、完成後の指標（`plannedMetrics`）で電力の余力がその需要以上あるときだけ候補にする。足りなければ電力を使わない段階で建てる。
2. 「不足の解消」で、電力不足を食料不足より先に見る。電力が要る段階へ進化して食料不足を解消しようとしない。
3. 発電所の置き場がないときは、その用途（工業地区）で開拓することを優先する。
4. 安全策として、電力不足のときの生産に下限（例：0.3〜0.5。`OPERATION_FLOOR` と同じ考え方）を設け、技術Lvが上がって街が止まることがないようにする。

<a id="gb-02"></a>
### GB-02 石材加工所の置き場がないと、街が止まる（重大）

**現象**（シナリオC：金貨を使わない・月12,000円）：技術Lv2（d13）で石材加工所が解放されると、それ以降の開拓に石材が要る。ところが工業地区に空きがなく、石材加工所が建たない。石材の生産は0のままで、開拓もできない。

- d13 から d120 まで区画は16のまま。人口は 425 で止まる。
- 都市資金は使い道がなく、d120 に 1,115,908 たまる。
- 120日のうち79日は、建設・Lvアップ・進化・開拓が1件もない。
- 工房（石材20）も建たないので、雇用充足率が 0.51 まで下がり、幸福度は 74 → 68 に下がる。

requirements.md FR-040（金貨・銀貨なしでも街が成長する）に反する。金貨をおまかせ交換すれば必要資源として石材が入るので抜け出せるが、交換しない人は気づけない。

**原因**：`plotCost`（[sim.ts](../src/game/city/sim.ts)）は「石材加工所が解放されているか」で石材を求めるかどうかを決めている（f4635fb の対策）。解放されていても、建っていなければ石材は作れない。不足の解消は石材の生産が 0.3/時未満のときに石材加工所を建てようとするが、置き場がなければ開拓を計画し、開拓には石材が要る、という循環になる。

似た問題として、石材加工所は1棟あれば「不足」と見なされなくなる（`production.stone < 0.3` だけで判断）。石材が開拓の制約になっていても2棟目は建たない。シナリオH（商業優先）では石材の在庫が 50〜113 にとどまり、都市資金 36万が手つかずになった。

**提案**

1. 開拓に石材を求める条件を「石材の生産がある（`production.stone > 0`）」にする。
2. 資材の不足は、生産がほぼ0かどうかではなく、計画列の先頭の計画を止めているかどうか（`cityNeeds` の不足）で判断し、2棟目以降の石材加工所も建てる。
3. 根本的には、開拓のたびに工業地区を1区画分は確保する（土地の取り合いで必須の施設が建たない、ということを防ぐ）。

<a id="gb-03"></a>
### GB-03 自動開発の優先順位で、下位の必要事項に資金が回らない（重大）

**(a) 「生産効率の改善」が下位をふさぐ**：`efficiency` には発動の条件がなく、進化・Lvアップの候補がいつもある。自動開発は「12時間以内に払える計画があれば、下位に資金を流さずに貯める」ので（[sim.ts](../src/game/city/sim.ts) `autoDevelop`）、バランス方針では「新産業への投資」と「景観改善」までほとんど届かない。

- シナリオA（50日）・C・D・F（120日）で、学校・病院・図書館・オフィス・鉄道駅・物流センター・未来都市センターは1棟も建たない。技術活用率は 0.70 のまま（公共施設のカバー0）で、公共施設による幸福度（最大+20）も入らない。
- 技術Lv4〜7 で解放される建物の多くを、自動開発が見せない。技術ゲージは「次に解放される施設」を出すが、それが街に建たない。
- 金貨を大量に入れたシナリオB では d30 に学校などが建った。`industry` が `efficiency` より上にある商業優先（シナリオH）でも建った。順番の問題であることがわかる。

**(b) 産業優先では住宅が建たない／収入が少ないと安い計画に流れ続ける**：産業優先は `efficiency` が `housing` より上にある。シナリオG では住宅2棟・人口23のまま50日止まった。そのときの計画列の先頭は発電所（都市資金600）・市場（640）で、収入は 16/時。12時間では払えないので飛ばされ、下位の安い計画（道路の進化 64 など）に資金が流れ続け、大きな計画の分がいつまでも貯まらない。

**提案**

1. `efficiency` に条件をつける。例：土地が埋まっている（新築の置き場がない）とき、または上位の項目の計画がないときだけにする。景観改善と同じく余剰資金のときだけにしてもよい。
2. 待つかどうかの判定を「12時間で払えるか」だけにしない。上位の計画が払えないときに下位へ流してよい額を、収入の一定割合（例：3割）までにして、上位の分も貯まるようにする。
3. 公共施設を「人口が公共施設のカバーを超えたら」発動する独立した必要事項にし、住宅の次あたりに置く（景観改善の中から出す）。
4. 方針のプリセットごとに、`balance-scenarios.ts` で50日・120日の推移を確かめる回帰テストを置く（人口が増え続けること、工事のない日が続かないこと）。

<a id="gb-04"></a>
### GB-04 発展Lvと技術Lvの時間軸がずれている（重大〜中）

**現象**

- 発展Lv6 には、どのシナリオでも13〜19日で届く（目安どおり）。その後の発展ptは区画数の上限の追加にしか効かない。
- 技術Lvは貯金額の絶対額（5,000／15,000／30,000／60,000／100,000／200,000円）。月12,000円（B＝60,000 の2割）の貯金では、Lv2 が13日、Lv3 が38日、Lv4 が75日、Lv5 が約150日、Lv6 が約250日（＝目標10万円の到達）。Lv7 は目標20万円以上のシーズンでないと届かない。
- 目標10万円のシーズンは約250日続き、そのうち230日以上は発展Lvが上限のまま。次の技術Lvまで1〜3か月、街の見た目はほとんど変わらない。シナリオC では d50 以降、人口も区画も変わらない。

**`balance.ts` の前提が速すぎる**：`balance.ts` の貯金スケジュールは40日で20万円（月15万円）で、上の想定（月12,000円）より技術Lvが12倍以上速く上がる。発展Lvの目安はこの前提で確かめているので、技術Lvとの釣り合いは確かめられていない。

**基準がばらばら**：技術Lvは円の絶対額、銀行Lvは目標に対する割合、債券の上限・倍率は B に比例する。予算や目標が小さい人は、技術の後半を見ないままシーズンが終わる。予算が大きい人は、同じ努力（貯金率）でも早く技術が上がる。

**提案**

1. 技術Lvの閾値を目標額に対する割合にする（例：0／5／15／30／50／75／100%）。または「絶対額」と「目標に対する割合」の小さい方にする。どのシーズンでも技術の全段階を見られ、最後の段階が目標達成と重なる。銀行Lvとの役割の重なりは、銀行Lv＝交換効率、技術Lv＝建物の解放と分けて説明できる。
2. 発展Lvの後半を伸ばす（`DEV_THRESHOLDS` の Lv5・6 を引き上げる、時間発展を Lv が上がるほど遅くする）か、発展ptの一部を記録の継続（記録した日数）に結びつけ、長いシーズンでも少しずつ変化が続くようにする。
3. バランスの目安を「日数」ではなく「目標到達までの割合」で決め直し、`balance-scenarios.ts` の real のシナリオで確かめる。

## 4. 中・軽の問題

<a id="gb-05"></a>
### GB-05 資材があふれ、都市資金も使い道がなくなる（中）

- シナリオA の d50：木材 1,343,616・石材 990,274。工場107棟の副産物で、d40〜d50 は木材が毎日8万以上増える。自動開発の制約は都市資金だけで、資材は事実上無限。
- シナリオF の d120：都市資金 9,239,847 が手つかず（人口上限・開拓は石材と費用で止まる）。シナリオC・D でも100万以上が残る。
- 金貨の価値は終盤に消える。d1 には1日の貯金 400G（都市資金4,000）が街の自前の収入（約240/日）の約17倍だが、シナリオD の d120 では街の収入（約52,000/日）の1割前後、シナリオF の d120 では 3% 程度。
- 「貯金すると街が育つ」という結びつきが、シーズンの後半ほど弱くなる。

**提案**：資材に上限（倉庫の容量）を設ける／工場を資材の加工（木材・石材を消費して都市資金にする）に変える／資材を都市資金に替える内部の市場を設ける／終盤の高額な使い道（ランドマーク、像・公園の装飾段階、都市プロジェクト）を用意する。金貨の交換量を街の規模（人口など）に連動させる方法もある。

<a id="gb-06"></a>
### GB-06 手動の建設・開拓は都市資金を使わない（中）

- 手動は「資材＋銀貨の手数料」で、都市資金は使わない（requirements.md 4.4）。手数料は建設 15〜40S（`feeBuild`）、開拓 15S。
- 都市資金がいちばん高いのは未来都市センター（10,000）。手動なら 15S と木材300・石材500 で建つ。商業タワー（5,000）も 20S。
- 即時完了は残り10分ごとに 2S で、金貨→銀貨は 1:1・無料。最長の工事（900分）でも 180S（約180円分）。
- 資材は中盤以降あまるので（GB-05）、手動は自動開発の唯一の制約（都市資金）を迂回できる。ゲームが壊れるわけではないが、「街は自律的に発展する」より手動のほうが圧倒的に速く、自動開発を見守る意味が薄れる。

**提案**：手動にも都市資金を求め、銀貨で一部を代わりに払えるようにする／手数料を都市資金のコストに比例させる（例：10 ＋ 都市資金 ÷ 100 S）／即時完了の単価を残り時間が長いほど上げる。

<a id="gb-07"></a>
### GB-07 債券倍率がほとんど体感できない（中）

- k ＝ min(1.5, 1 ＋ 債券 ÷ 6M)。B＝60,000 では、1.5倍に債券 180,000（＝上限 3M）が要る。目標10万円のシーズンでは届かない。シナリオE（貯金をすべて債券に入れる）でも d120 に k＝1.13。
- 倍率は時間発展（2pt/時）にだけ掛かる。発展Lvは13〜19日で上限になり、その後の発展ptは区画数の上限の追加にしか効かず、区画は費用で止まる（GB-12）。
- シナリオD と E の d120 の差は、発展pt 8,452 → 8,595（+1.7%）、人口 3,140 → 3,190。債券を持つ利点は、ほぼ「資源つき」と「精算の肩代わり」だけ。

**提案**：倍率の基準を目標額にする（例：1 ＋ 債券 ÷ 目標）／建設時間や人口増加にも効かせる（requirements.md 4.5 の「時間発展にだけ掛ける」を見直す）／効果が小さいなら倍率をやめ、ゲージの表示を簡単にする。

<a id="gb-08"></a>
### GB-08 物流効率がいつも100%（中）

- 未舗装道路1マスで物流容量6（建物6棟分）。区画を開くと十字の道路9マス（容量54）が敷かれるが、1区画に入る 2×2 の建物は4棟程度。
- すべてのシナリオで物流効率は 1.00。「物流の改善」は物流効率が90%未満のときだけ発動するので、鉄道駅・物流センターは建たない。`LOGISTICS_FLOOR` も効いていない。

**提案**：道路の物流容量を 0.5〜1 に下げる、建物を Lv や大きさで重みづけして数える、区画を開いたときの道路を容量に数えない、のどれか。物流を使わないなら、鉄道駅・物流センターを別の役割（雇用・幸福度）に変える。

<a id="gb-09"></a>
### GB-09 自動化の段階で仕事枠が減り、工場が乱立する（中）

- 仕事枠は 大規模工場10 → 自動化工場6、大規模農場4 → 自動農場2 と減る。技術Lv6 で進化すると雇用が足りなくなり、「雇用不足の解消」はまず工業を建てる（商業の供給が人口を上回っているとき）。
- シナリオA：工場は 13棟（d20）→ 44棟（d30、技術Lv6 は d28）→ 107棟（d50）。住宅は27棟。工場の副産物で資材があふれ（GB-05）、住宅と工業の隣接で幸福度が 74 → 58 に下がる。

**提案**：自動化の段階で仕事枠を減らさない（または、減らす代わりに公共施設のカバーで生産が上がるようにする）。雇用不足の解消では、資材が余っていれば商業・オフィスを先に建てる。

<a id="gb-10"></a>
### GB-10 債券で払って戻すたびに資源がつく（中）

- `bondResourceEligible`（[bond.ts](../src/game/bond.ts)）は、債券が 0〜3M の範囲に入る分すべてに資源をつける。マイナスを0に戻す分には資源がつかないが、0以上の範囲で減って戻る分にはつく。
- 購入は、ユーザ通貨のあと「未回収の金貨 → 所持金貨 → 債券」の順に払う。金貨をすぐ街に交換する人は、購入を債券で払うことになる。その後、採掘の債券化（債券化率 r > 0）や金貨→債券の交換で戻すと、同じ額の資源がもう一度入る。
- 例：B＝60,000、債券が上限の 180,000。30,000円の購入を債券で払い（手数料は上限 50S）、債券化で 30,000 戻すと、30,000G 分の資源（都市資金なら30万〜45万）がもう一度入る。金貨で払う人にはこの分がない。
- 貯金額（技術Lv・目標）は正しく減るので、影響は街の資源だけ。ただし設計原則2（お金を使うより節約を有利にする）・5（支出の扱いで有利不利が出ない）とずれる。

**提案**：シーズン中の債券の最高到達額を持ち、その額を超えて入った分（上限 3M まで）だけに資源をつける。マイナスの返済と同じく、使った分を戻すときには資源をつけない。

<a id="gb-11"></a>
### GB-11 おまかせ交換が1つの資源に偏る（軽）

- 必要割合は「計画列で最初に足りなくなった1件」の不足だけで決まる（needs-based-exchange.md §4.2）。必要量を上限にしない（NX-14）のは意図どおりだが、大きな額では1つの資源に偏る。
- シナリオB の d7：その日の 10,000G がほぼすべて木材（約10万）になった。木材はその後も減らず、d50 には162万になる。臨時の収入を即時貯蓄（債券化の資源）にしたときも同じことが起きる。

**提案**：計画列を先頭から順に満たすように振り分け、満たしきった残りを拡張計画の割合で振り分ける。

<a id="gb-12"></a>
### GB-12 区画数の上限が後半は効いていない（軽）

- 開拓の費用は 1.2^n（`PLOT_COST_GROWTH`）。n＝40（41区画目）で 1,470倍（木材88,000・石材29,000・都市資金22万）、n＝50 で 9,100倍（都市資金136万）。
- どのシナリオでも最終的な区画は 16〜57 で、発展Lv6 の上限（40 ＋ 150ptごとに4）や `MAX_PLOTS`（400）より先に、費用で止まる。発展Lvで地区が広がる（FR-035）という結びつきが後半は見えない。

**提案**：伸び率を下げて（1.08〜1.1）上限で止めるか、上限をやめて費用だけで決める。どちらでも、区画数の目安を `balance-scenarios.ts` で確かめる。

<a id="gb-13"></a>
### GB-13 公園の幸福度は月額によらない（軽）

- 公園の幸福度は、月額に関係なく1つ目+6、次から0.6倍（上限+15）。税と人口増加は (0.5 ＋ 幸福度/100) に比例するので、+6 で約5%増える。
- 中盤（税 1,000/時）なら月に約36,000の都市資金になる。月額500円のサブスクで減る採掘 500G（都市資金5,000〜7,500）の約5倍。月額が安いほど効率がよい。
- 実際には都市資金があまるので（GB-05）影響は小さいが、設計原則2 とはずれる。

**提案**：幸福度を公園の大きさ（`parkSize`）に応じて変える、または1つ目の効果を下げる。

<a id="gb-14"></a>
### GB-14 配当Lvは予算の大きさで上がる（軽）

- 配当Lv（金鉱Lv）は累計の採掘量（購入に使った分を含む）で決まり、B が大きいほど速く上がる。B＝60,000 では約75日で Lv6（150,000G）。
- 節約・貯金とは関係がない。影響は金貨の交換効率（最大+20%）だけ。

**提案**：「都市に使った金貨＋債券化した額」（貯金額の累計）を基準にする。

## 5. 直す順番の提案

1. **街が止まる・壊れる問題**（GB-01・GB-02・GB-03）：自動開発の判断の修正で、値の調整はほとんど要らない。直したら、`balance-scenarios.ts` の A〜H で「人口が増え続ける」「工事のない日が続かない」「技術Lvが上がった後に生産が落ちない」を確かめる。
2. **時間軸の見直し**（GB-04）：技術Lvの閾値を目標に対する割合にするか決める。決めたら、発展Lv・開拓の費用（GB-12）・債券倍率（GB-07）をその時間軸に合わせる。
3. **資源の流れの整理**（GB-05・GB-06・GB-09・GB-08）：資材の使い道と手動のコストを決める。終盤まで金貨を街に使う意味が残るようにする。
4. **小さな整合**（GB-10・GB-11・GB-13・GB-14）：設計原則とのずれを直す。

## 6. 再現方法

```bash
npx tsx scripts/balance-scenarios.ts                                    # C：real・金貨なし・120日
GOLD=city npx tsx scripts/balance-scenarios.ts                          # D
GOLD=bond npx tsx scripts/balance-scenarios.ts                          # E
SAVE=0.5 GOLD=city npx tsx scripts/balance-scenarios.ts                 # F
PACE=fast DAYS=50 npx tsx scripts/balance-scenarios.ts                  # A（balance.ts 相当）
PACE=fast DAYS=50 GOLD=city npx tsx scripts/balance-scenarios.ts        # B
PACE=fast DAYS=50 PRESET=industry npx tsx scripts/balance-scenarios.ts  # G
PACE=fast DAYS=50 PRESET=commerce npx tsx scripts/balance-scenarios.ts  # H
```

その他の変数：`B`（月間自由予算、既定 60,000）、`GOAL`（目標、既定 100,000）、`EVERY`（何日ごとに表示するか、既定 10）。120日のシナリオは1本1〜2分かかる。
