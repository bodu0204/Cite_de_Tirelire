# 債券・ユーザ定義通貨 改修 As-Is / To-Be

作成日：2026-10-18（2026-10-19 改訂：§12 の回答と追加要望を反映。同日、残りの論点をすべて確定）
関係：[requirements.md](requirements.md) 2.2・3.2・3.6・4.5・4.8・5・9、[mine.ts](../src/game/mine.ts)、[ops.ts](../src/server/ops.ts)、[game.ts](../src/server/game.ts)、[sim.ts](../src/game/city/sim.ts)、[view.ts](../src/server/view.ts)

## 1. 目的

金貨・銀貨に加えて、次の2つを追加する。

- **債券**：急な出費に備えるためのお金。持っているほど街の発展が速くなり、足りない支払いを肩代わりする。マイナスになり得る唯一の通貨。
- **ユーザ定義通貨**：「食費コイン」のように、名前・アイコン・使えるジャンル・発生のタイミング・余りの扱いをプレイヤーが決める通貨。何種類でも定義できる。自由予算の内訳として扱い、その分を採掘から差し引く。

あわせて、金貨は**マイナスにならない**仕様に戻す（現行の「採掘負債」を債券のマイナスに置き換える）。

## 2. 用語と前提

| 用語 | 定義 |
|---|---|
| M（月に使えるお金） | 月間自由予算 B（`User.monthlyBudget`）。サブスク・ユーザ通貨は引かない（決定済み） |
| 債券上限 | 3M。採掘の債券化と、ユーザ通貨の余りの債券化が止まる額 |
| 債券倍率 | 債券の残高で決まる発展速度の倍率（§4.2） |
| ジャンル | 購入記録のカテゴリ。ユーザ通貨が使える範囲を決める |
| 発生ルール | ユーザ通貨が「いつ・いくら」発生するかの1つの決まり。1つの通貨に複数持てる（§5.2） |
| ロット | ユーザ通貨の1回分の発生。余りの期限をロットごとに持つ |
| C（月の通貨発生額） | その月にユーザ通貨が発生する額の合計（全通貨・全ルール）。採掘から差し引く（§5.5） |

- 債券・ユーザ通貨はどちらも **1単位 ＝ 1円相当**（金貨と同じ。D-9）。
- 端数は金貨と同じく内部で 10⁻⁶ 単位の固定小数点で持ち、残高は整数で扱う。

## 3. As-Is（現状）

### 3.1 通貨

| 通貨 | 獲得 | 用途 | マイナス |
|---|---|---|---|
| 金貨 G | 金鉱の時間採掘（タップで回収） | 資源交換・像の積立・銀貨への交換・購入の精算 | **表示上マイナスになる**（手持ち − 採掘負債） |
| 銀貨 S | 記録報酬・金貨からの交換 | 資源交換・手動操作の手数料 | ならない |
| 積立金貨 | 像への積立 | ほしい物の購入に充当 | ならない |

台帳の通貨は `GOLD / SILVER / RESERVED` の3種（`Currency` enum）。

### 3.2 金鉱の採掘量

毎分の採掘量 ＝ max(0, B − S) ÷ その月の分数。S はサブスクの月額換算。

### 3.3 購入の精算（[ops.ts](../src/server/ops.ts) `settle`、[mine.ts](../src/game/mine.ts) `settlePurchase`）

対象は「進行中シーズン・サブスク以外・当月の日付」の購入。次の順に差し引く。

1. 像の積立金貨（ほしい物に紐付けた購入のみ）
2. 未回収の金貨
3. 所持金貨
4. **採掘負債**（今後の採掘から先に相殺される。所持金貨はマイナス表示）

- 負債がある間は、採掘分の**全額**がまず負債の返済に回り、手持ちに入った金貨も保存時に自動で返済に充てる（[game.ts](../src/server/game.ts) `repayDebtFromHeld`）。
- 月末に残った負債は `MonthlyOverspend`（予算超過）として記録し、0に戻す。**翌月へ繰り越さない。**
- 購入の編集・削除の払い戻しは、負債を先に減らし、残りを所持金貨へ戻す（`refundPurchase`）。支払いの内訳は保存していない（`settledAmount` と `reservedApplied` のみ）。

### 3.4 発展速度（[sim.ts](../src/game/city/sim.ts) `tick`）

時間発展 ＝ `DEV_PER_HOUR`（2pt/時）× 都市稼働係数（0.3〜1.0）。通貨の残高は発展速度に影響しない。

### 3.5 貯金目標

- 判定（技術Lv・銀行Lv・GOAL_REACHED）＝ 記録した貯金純増額のみ。
- 表示の達成率 ＝（純増額 ＋ 見込み貯金）÷ 目標額（D-11）。

### 3.6 ジャンル（カテゴリ）

`Purchase.category` は任意入力の自由文字列（最大50文字）。一覧・マスタはなく、表示に使うだけ。

### 3.7 放置計算

[game.ts](../src/server/game.ts) `load` で「金鉱の採掘を現在まで」→「街を現在まで」の順に**別々に**計算する。街の計算は金鉱の状態に依存しない。

## 4. To-Be：債券

### 4.1 一覧

| ID | 要件 |
|---|---|
| BND-01 | 債券は進行中シーズンごとの残高を持つ（`Season.bond`、整数、マイナス可） |
| BND-02 | 債券がプラスのとき、残高に応じて時間発展が速くなる（§4.2）。**マイナスでも遅くはならない**（設計原則5） |
| BND-03 | 購入の精算で金貨（とユーザ通貨）が足りない分は、自動で債券から支払う。債券はマイナスになってよい。**金貨・銀貨・ユーザ通貨はマイナスにならない**（§6） |
| BND-04 | 債券を使ったら、銀貨で手数料を払う。手数料 ＝ min(50, ⌈使った債券 × 10%⌉)（500 以下なら10%、500 を超えたら一律 50S）。銀貨が足りない分は、同じ数だけ債券から引く（1S ＝ 1債券。G→S が1:1のため） |
| BND-05 | いつでも金貨を債券に 1:1 で替えられる（無料）。債券 → 金貨は不可（急な出費用として取っておく） |
| BND-11 | 債券は現実の購入の精算にだけ使う。資源交換・手動操作の手数料などゲーム内の操作で金貨・銀貨が足りないときは、債券を使わず現行どおり失敗する |
| BND-12 | 新シーズンで債券は0にリセットする（マイナスも持ち越さない） |
| BND-06 | 採掘の一部を債券に回せる（債券化率 r：0〜100%、10%刻み、ユーザー設定）。債券が上限 3M に達したら自動で止まり、超える分は金貨のまま |
| BND-07 | 債券がマイナスの間は、採掘の **max(r, 20%)** を強制的に債券に回す。0に戻ったら r に戻る |
| BND-08 | 債券の残高を貯金目標の**表示の**達成率に含める。判定には今は含めない（§4.4） |
| BND-09 | 債券化した採掘分は、回収を待たずに債券へ直接入る。金鉱Lvの累計（`totalCollected`）には債券化分も含める（債券化すると金鉱Lvが遅れる、を防ぐ） |
| BND-10 | 金貨→債券の交換は見込み貯金に加えない（債券は達成率に直接含まれるため、二重に数えない） |

### 4.2 債券倍率

```
b = 債券の残高
b ≤ 0 または M ≤ 0 → 1.0
b > 0 かつ M > 0   → min(1.5, 1 + b / (6M))
```

債券倍率 k は**時間発展にだけ**掛ける。

| 対象 | As-Is | To-Be |
|---|---|---|
| 時間発展 | `DEV_PER_HOUR × 都市稼働係数` | `DEV_PER_HOUR × 都市稼働係数 × k` |
| 建設時間・人口増加 | — | 変えない |
| 建設完了・Lvアップ・進化の発展pt（+3/+1/+4） | — | 変えない |

- 時間発展は発展ptの一部なので、発展Lvに届くまでの速さは最大でも1.5倍未満に収まる。発展Lvの目安（requirements.md 4.2）は大きく崩れない見込みだが、`scripts/balance.ts` で k ＝ 1.5 のときも確かめる。

例（M ＝ 60,000）：

| 債券 | 倍率 |
|---:|---:|
| −3,000 | 1.0 |
| 0 | 1.0 |
| 90,000 | 1.25 |
| 180,000（＝3M） | 1.5（上限） |
| 300,000 | 1.5 |

倍率が上限 1.5 になる額（6M × 0.5 ＝ 3M）と、債券化が止まる上限 3M は一致する。上限を超えて債券を持っても得がないので、余りは金貨に回る設計で整合している。

### 4.3 採掘の分け方

1分ごとの採掘量 m（§5.5 の差し引き後）を次のように分ける。

| 債券の状態 | 債券へ | 金貨（未回収）へ |
|---|---|---|
| b < 0 | m × max(r, 20%) | 残り |
| 0 ≤ b < 3M | min(m × r, 3M − b) | 残り |
| b ≥ 3M | 0 | m |

- 区間の途中で b が 0 や 3M に達する時刻で区間を区切る（現行の「月の境界・サブスクの変更」と同じ扱い）。
- 債券化分の端数は `Season.mineBondFraction`（µ単位）に貯め、整数部分を債券へ移す。
- 現行の「採掘をまず負債の返済に回す」処理と、`repayDebtFromHeld` は廃止する。

### 4.4 貯金目標への含め方

| 用途 | As-Is | To-Be（今回） | 将来 |
|---|---|---|---|
| 表示の達成率 | 純増額 ＋ 見込み貯金 | 純増額 ＋ 見込み貯金 ＋ **債券**（マイナスなら減らす。全体は0未満にしない） | 同じ |
| 技術Lv・銀行Lv・GOAL_REACHED | 純増額 | 純増額（変えない） | 債券を含める |

将来、判定に含めるときは次を先に決める。

- **二重計上の防止。** 債券にしたお金を現実でも貯金として記録すると、同じお金を2回数える。例：貯金を記録するときに「債券から移す」を選べるようにし、その額だけ債券を減らす。
- **技術Lvの根拠。** 今は「現実の貯金の最高到達額」で、引出でも下がらない。債券は精算で減り、マイナスにもなるので、最高到達額に含めるかを決める。

切り替えを1か所で済ませるため、達成率の計算は「純増額・見込み・債券」を受け取る1つの関数にまとめ、判定に何を含めるかを引数で選ぶ形にしておく。

### 4.5 金貨のマイナス表示の廃止

- `goldBalance`（手持ち − 負債）の表示をやめ、所持金貨は常に0以上。
- 「マイナスの間は金貨を使う操作ができない」制限は、債券のマイナスでは**かけない**（金貨は自分の手持ち分だけ使える）。
- 予算超過 `MonthlyOverspend` は「その月に不足分として債券から払った額」の記録に意味を変えて残す（履歴・エクスポート用）。月末に債券を0に戻すことはしない（マイナスは翌月に繰り越し、BND-07 で返す）。

### 4.6 設計原則5との関係

「現実の支出を隠すことが有利にならない」に照らして、債券がマイナスのときの影響を確認する。

| 影響 | As-Is（採掘負債） | To-Be（債券のマイナス） | 判断 |
|---|---|---|---|
| 発展速度 | 影響なし | 影響なし（0.5倍は要件から外した） | 問題なし |
| 採掘 | 全額を返済に回す | max(r, 20%) を返済に回す | 今より軽い |
| 手数料 | なし | 債券を使った額の10%、上限 50S を銀貨で払う | 上限が購入記録の報酬（50S）と同じなので、記録で得る銀貨を超えない（1日の報酬上限 300S に達した日を除く） |

## 5. To-Be：ユーザ定義通貨

### 5.1 定義できる項目

| ID | 項目 | 内容 |
|---|---|---|
| CUR-00 | 数 | 何種類でも定義できる（上限なし） |
| CUR-01 | 名前・アイコン | 名前（最大20文字）とアイコン（絵文字1文字。結合文字を含む1書記素として検証する） |
| CUR-02 | 使えるジャンル | 1つ以上のジャンル。そのジャンルの購入にだけ使える |
| CUR-03 | 発生ルール | 1つ以上。種類と組み合わせは §5.2 |
| CUR-04 | 余りの扱い | §5.3 |
| CUR-05 | 有効期間 | 開始日（省略時は作成日）・終了日（任意）。サブスクと同じ形。周期の起点は開始日。期間外の発生はしない |

定義はユーザー単位でシーズンをまたいで引き継ぐ（サブスクと同じ）。残高はシーズンごと。

### 5.2 発生ルール

**As-Is（最初の要望）：** 1つの通貨は「毎分」か「周期的な日」のどちらか1つで発生する。
**To-Be：** 1つの通貨に発生ルールを**複数**持てる。種類に「カレンダー指定日」を加える。どの種類も省略でき、「カレンダー指定日」だけの通貨も作れる（ルールは最低1つ）。

| 種類 | 設定 | 発生の時刻と量 | 1通貨あたり |
|---|---|---|---|
| 毎分 | 月あたりの量（C にそのまま足せる） | 金貨と同じく毎分、端数は µ 単位で保持 | 0〜1個 |
| N週ごと | N（1〜12）、曜日（複数可）、1回の量 | 起点日を含む週から N 週ごと、指定曜日の 0:00 | 0個以上 |
| 毎月・日付 | 日（複数可、1〜31）、1回の量 | 毎月その日の 0:00。その月にない日（31日など）は月末日 | 0個以上 |
| 毎月・第X週の曜日 | X（第1〜4・最終、複数可。第5は出さず「最終」で代用）、曜日（複数可）、1回の量 | 「第X◯曜日」＝その月の X 回目のその曜日。X × 曜日の全組み合わせ | 0個以上 |
| N月ごと | N（1〜12）、日（複数可）、1回の量 | 起点日の月から N か月ごと、その日の 0:00（ない日は月末日） | 0個以上 |
| **カレンダー指定日** | 日付（複数可、YYYY-MM-DD）、1回の量 | 指定した日の 0:00 | 0個以上 |

- 量はルールごとに決める。例：食費コイン ＝「毎週月曜 7,000」＋「12/24 に 5,000」。
- 同じ日に複数のルールが当たれば、それぞれ発生する（合算して1ロットにする）。
- 時刻はユーザーのタイムゾーン基準（[time.ts](../src/game/time.ts)）。
- 発生はシーズン中だけ（金鉱と同じく、新シーズン開始後の時間のみ）。過ぎた日付のカレンダー指定日は発生しない。

### 5.3 余りの扱い

| 設定 | 動き |
|---|---|
| そのまま残す | 期限なし。シーズン中は残り続ける |
| N日後に債券へ | 各ロットの発生から N 日後の 0:00 に、残りを債券へ移す。債券が上限 3M に達したら、超える分は金貨（所持）へ |

- 毎分型のロットは1日単位にまとめる（その日の0:00に発生したものとして期限を数える）。
- 支払いは期限の近いロットから使う（先入れ先出し）。
- 期限による移動は放置中も進む（§7）。

### 5.4 支払いに使える範囲

- ユーザ通貨は、ジャンルが一致する**購入の精算にだけ**使う。資源交換・手数料・像の積立・金貨への交換には使えない。
- 1つの購入に複数のユーザ通貨が一致したら、期限の近いロット順、同じなら通貨の並び順で使う。

### 5.5 採掘からの差し引き

ユーザ通貨は自由予算の内訳なので、発生する分だけ金貨の採掘を減らす（サブスクと同じ考え方。予算の二重計上を防ぐ）。

```
毎分の採掘量 ＝ max(0, B − S − C) ÷ その月の分数
C ＝ その月に発生する予定の額の合計（全通貨・全ルール、有効期間内のみ）
    毎分ルールは月あたりの量そのもの
```

- C は暦から事前に決まるので、月の初めに求めて月の間は一定。週ごとのルールは月によって回数が変わり、C も変わる。
- 例（B ＝ 60,000、S ＝ 6,000、食費コイン 毎週月曜 7,000）：

  | 月 | 月曜の数 | C | 採掘（月） |
  |---|---:|---:|---:|
  | 2026-10 | 4 | 28,000 | 26,000 |
  | 2026-11 | 5 | 35,000 | 19,000 |

- 月の途中で通貨の定義を変えたら、変更時点までは前の C で採掘済みとし、そこから新しい C で採掘する（予算変更と同じ扱い）。
- シーズンが月の途中から始まった場合は、サブスクと同じく月の分数で按分される（採掘は始まった時刻からなので）。
- **B − S − C が負になる設定は保存を拒否する。** 確かめる範囲は今月から12か月先まで（カレンダー指定日がそれより先にあれば、その月まで）の各月。1か月でも負なら拒否し、どの月がいくら超えるかを返す。確かめる時：
  - ユーザ通貨の作成・変更（ルール・有効期間・量）
  - 月間自由予算 B の変更（設定画面）
  - サブスクの登録・変更は拒否しない（現実の契約の記録を妨げない。設計原則5）。超える月があれば警告し、その月の採掘は max(0, …) で0になる
- 12か月より先で負になる場合に備え、採掘の式の max(0, …) は残す。
- 金鉱画面の採掘速度の内訳に、サブスクと並べてユーザ通貨を表示する。

## 6. To-Be：購入の精算順

対象（当月・サブスク以外）は現行と同じ。順番を次に変える。

| 順 | As-Is | To-Be |
|---|---|---|
| 1 | 像の積立金貨 | 像の積立金貨（変更なし） |
| 2 | 未回収の金貨 | **ジャンルが一致するユーザ通貨**（期限の近い順） |
| 3 | 所持金貨 | 未回収の金貨 |
| 4 | 採掘負債（金貨がマイナス表示） | 所持金貨 |
| 5 | — | **債券**（マイナス可）＋ 銀貨の手数料（10%、上限 50S。不足分は債券から） |

### 6.1 例

食費 5,000円の購入。食費コイン 1,200、未回収 300G、所持 1,000G、債券 10,000、銀貨 30S。

| 支払い元 | 額 |
|---|---:|
| 食費コイン | 1,200 |
| 未回収の金貨 | 300 |
| 所持金貨 | 1,000 |
| 債券 | 2,500 |
| 手数料：銀貨 | 30（50 のうち。2,500 の10%は 250 だが上限 50） |
| 手数料：不足分を債券から | 20 |

結果：食費コイン 0、金貨 0、銀貨 0、債券 10,000 − 2,500 − 20 ＝ **7,480**。

債券 0 から不足 300 なら：手数料は 30S（10%）→ 債券 **−300**、銀貨は 30 減る。
債券 0 から不足 3,000 なら：手数料は 50S（上限）→ 債券 **−3,000**。銀貨が 0 なら 50 を債券から引き **−3,050**。以後、0に戻るまで採掘の20%以上が債券に回る。採掘が月 60,000 なら月 12,000（1日 400）が債券に回り、約8日で0に戻る。発展速度は変わらない。

### 6.2 支払い内訳の保存と払い戻し

- 購入ごとに支払いの内訳（通貨・ロット・額、手数料の銀貨・債券）を保存する（§8 `PurchasePayment`）。
- 編集で増額したら、増えた分を上の順で追加精算する。
- 減額・削除の払い戻しは**逆順**：債券 → 所持金貨 → ユーザ通貨（元のロットへ。期限切れなら、その場で余りの扱いを適用）→ 像の積立金貨。
- 手数料は「その購入で債券から払った額の合計」から計算し直し、差額を返す（誤入力の修正で損をしない。設計原則3）。例：債券 2,500 → 400 に減額すると、手数料は 50 → 40 になり 10 を返す。手数料のうち債券から引いた分があれば、そちらから先に返す。
- 増額で債券の支払いが増えたときも同じく計算し直し、上限 50S を超えて取らない。
- 締めた月・別シーズンの記録は精算し直さない（現行どおり）。

## 7. To-Be：放置計算

債券倍率が街の発展に効くため、金鉱と街を**別々に計算できなくなる**。

| | As-Is | To-Be |
|---|---|---|
| 順番 | 金鉱を現在まで → 街を現在まで | 10分ティックごとに「金鉱（債券化含む）→ ユーザ通貨の発生・期限 → 街の1ティック」を繰り返す |
| 街が参照する通貨 | なし | ティック開始時の債券残高（倍率）。そのティックの時間発展に使う |
| 金鉱が参照するもの | 予算・サブスク | 予算・サブスク・**ユーザ通貨の月の発生額 C** |
| 決定性 | 同じ経過時間なら同じ結果 | 同じ（ティック境界は絶対時刻に揃える。µ単位の切り捨て誤差は現行の金鉱と同程度） |

- 最後の端数（ティック境界 〜 現在）は金鉱・ユーザ通貨だけ進め、街は次のティックまで待つ（現行どおり）。
- 発生ルールは「ある時刻の次の発生時刻」と「ある月の発生額の合計」を返す関数にして、1分ずつ調べない。通貨の数に上限がないため、1回の計算で扱う発生・期限のイベントは時刻順の一覧にまとめて処理する。
