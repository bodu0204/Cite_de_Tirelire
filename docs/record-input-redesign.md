## 1. 目的

銀鉱（記録）の入力を、**収入・支出・誤差調整**の3種類に整理する。

- **収入**：月の収入（自由予算がベース）と臨時の収入を記録し、ベースからの差分や臨時の収入を、どの通貨に・いつ・どう振り分けるかを決められるようにする。入力時に資源のおまかせ購入もできる。
- **支出**：普通の支出に加えて、サブスク・ほしい物の支払いを設定から作ったベースで「保存」ボタンひとつで記録できるようにする。ベースとの差分は決まった順番で解消する。
- **誤差調整**：記録から推測した「手元にあるお金」を表示し、実際との誤差を入力して解消できるようにする。

差分の解消は3種類で共通のルールにする（§4）。

## 2. 用語と前提

| 用語 | 定義 |
|---|---|
| B | 月間自由予算（`User.monthlyBudget`）。月の収入のベースになる |
| S / C | 月のサブスク額 / 月のユーザ通貨の発生額（requirements.md 2.1）。採掘は max(0, B − S − C) |
| ベース | 設定（自由予算・サブスク・ほしい物の価格）から作る、記録の初期値 |
| 差分 | 実際の額 − ベース を、**手元のお金から見た向き**で表したもの。手元のお金が予定より多くなる向きを **＋差分**、少なくなる向きを **−差分** とする（§4.1） |
| 振り分け | 収入（差分・臨時）を、量・通貨・時期・方法の組で通貨に入れる指定（§5.3） |
| おまかせ交換 | 金貨を都市の必要資源の割合で資源・都市資金に交換すること（needs-based-exchange.md §5） |
| 手元のお金の推測 | 記録から計算した、現実の自由予算の残り（§7.2） |
| 債券上限 | 3M（M ＝ B。`bondCap`） |

- 1G ＝ 1円相当（D-9）、ユーザ通貨も 1単位 ＝ 1円相当。
- 技術Lv・銀行Lv・目標達成の判定は、これまでどおり記録した貯金の実額だけで行う（3.6）。本書の変更はこの原則を変えない。

## 3. As-Is（現状）

### 3.1 記録画面（SCR-02、[records/page.tsx](../src/app/(game)/records/page.tsx)）

- タブは「購入を記録」「貯金を記録」「記録履歴」の3つ。
- **収入を記録する手段がない。** 自由予算 B は設定値で、金鉱が毎分 (B − S − C) ÷ 月の分数 を自動で採掘する（[mine.ts](../src/game/mine.ts) `accrue`）。実際の月収が B と違っても、ゲームには反映できない。
- 臨時の収入（ボーナス・お祝い・払い戻しなど）を通貨にする手段もない。

### 3.2 購入（[ops.ts](../src/server/ops.ts) `recordPurchase`・`settle`、[settle.ts](../src/game/settle.ts) `pay`）

- 金額・日付・名称（必須）、ジャンル・メモ（任意）、「サブスクの支払い」フラグ、ほしい物の紐付け。
- 精算順：像の積立金貨（紐付けたほしい物のみ）→ ジャンルが一致するユーザ通貨 → 未回収金貨 → 所持金貨 → 債券（マイナス可）＋銀貨の手数料。
- 当月以外の日付、サブスクの支払い、シーズン外の記録は精算しない。
- 記録前に支払い内訳をプレビューできる（`/api/purchases/quote`）。

### 3.3 サブスクの支払い（SCR-06）

- サブスクの登録内容（金額・周期・開始日・解約日）から月額換算 S を採掘から差し引いている。
- 支払いの記録は、購入フォームで毎回 金額・名称を手入力し「サブスクの支払い」にチェックを入れる。登録済みのサブスクとは**紐付かない**（どのサブスクの何月分かを持たない）。
- 「サブスクの支払い」は精算しないので、**登録額と実際の請求額がずれても（値上げ・日割り・為替）ゲームには反映されない。**

### 3.4 ほしい物の購入（SCR-05）

- 購入フォームでほしい物を選ぶと、積立金貨を min(積立, 購入額) だけ精算に充て、残りは通常の精算順で払う。
- 金額はほしい物の価格から入らず、毎回手入力する。
- 購入額が積立より安かったとき、**余った積立金貨は像に残ったままになり、使い道がない。**

### 3.5 貯金と見込み貯金

- 貯金（追加・引出）の記録は技術Lv・銀行Lv・達成率の根拠。
- 金貨で資源を得た額は「見込み貯金」に加わり、貯金を記録すると0に戻る（実額に置き換わる）。
- 「手元にいくらあるはずか」を表示する機能はない。記録漏れ（未記録の支出・収入）を見つけて直す手段は、購入・貯金を後から追加することだけ。

### 3.6 現状の問題

| # | 問題 |
|---|---|
| P1 | 収入の記録がなく、実際の月収と B の差がゲームに入らない |
| P2 | 臨時の収入を通貨にできない（使い道が「記録しない」しかない） |
| P3 | サブスク・ほしい物の支払いを毎回手入力する必要がある |
| P4 | サブスクの請求額のずれ、ほしい物の値引きが反映されない（余った積立金貨が残る） |

## 4. To-Be：差分の解消ルール（共通）

### 4.1 差分の向き

差分は「記録したことで手元のお金が予定より増えるか・減るか」で向きを決める。

| 記録 | ＋差分（手元が予定より多い） | −差分（手元が予定より少ない） |
|---|---|---|
| 月の収入 | 実際の月収 ＞ B | 実際の月収 ＜ B |
| サブスクの支払い | 請求額 ＜ 登録額 | 請求額 ＞ 登録額 |
| ほしい物の購入 | 購入額 ＜ 価格（積立が余る） | 購入額 ＞ 価格 |
| 誤差調整 | 実際の手元 ＞ 推測 | 実際の手元 ＜ 推測 |

### 4.2 ＋差分：債券 → おまかせ交換

| ID | 要件 |
|---|---|
| RC-01 | ＋差分 d は、まず債券に入れる。入れる額は min(d, max(0, 上限 − 債券))。債券がマイナスならその返済にも充たる |
| RC-02 | 債券に入った分のうち 0〜上限の範囲に入る分には、これまでどおり同じ量の金貨でおまかせ交換した資源がつく（needs-based-exchange.md §6.2 の式。手数料なし・見込み貯金に加えない） |
| RC-03 | 債券が上限に達して入りきらない残りは、金貨としておまかせ交換する。手数料は1回 5S（銀貨が足りなければ手数料なしで交換する※Q7）。この額は見込み貯金に加える（金貨で資源を得たのと同じ） |
| RC-04 | 確定前に「債券 +x（資源つき y）・おまかせ z G → 木材・石材・食料・都市資金」をプレビューする |

> 例（M ＝ 60,000、上限 180,000）：債券 175,000 のとき ＋差分 8,000 → 債券に 5,000（資源つき 5,000）、残り 3,000G をおまかせ交換。

### 4.3 −差分：金貨 → 債券

| ID | 要件 |
|---|---|
| RC-11 | −差分 d は、未回収金貨 → 所持金貨 → 債券（マイナス可）の順で減らす。購入の精算（settle.ts `pay`）からユーザ通貨を除いたものと同じ |
| RC-12 | 債券から減らした分には、購入と同じ銀貨の手数料（使った債券の10%、上限50S、銀貨の不足分は債券から）をかける※Q8 |
| RC-13 | 債券から減らした分は、その月の `MonthlyOverspend` に加える |
| RC-14 | 過去に得た資源・建物は没収しない（設計原則4） |

### 4.4 計算の置き場所

- [settle.ts](../src/game/settle.ts) に `absorbSurplus(purse, d, needs, lv)`（RC-01〜03）と `absorbShortfall(purse, d, payments)`（RC-11〜13。`pay` をロットなしで呼ぶ）を追加し、3種類の記録から共通に使う。
- 解消の内訳は支払い内訳と同じ形（`Payment[]`）で記録ごとに保存し、編集・削除のときに逆順で戻す（§8.3）。

### 5.3 振り分け

振り分けは次の行の組。合計は振り分ける額（＋差分、または臨時の収入の全額）と一致させる。

| 項目 | 選べる値 |
|---|---|
| 量 | 円（または割合％。端数は最後の行に寄せる） |
| 通貨 | 金貨 / 債券 / ユーザ通貨（いずれか1つ） |
| いつ | 即時 / 指定日（1日〜複数日） / 期間で均等（開始日〜終了日） |
| どう | 一括 / 日ごと均等 / 毎分（期間で均等のとき） |

- 金貨：即時・指定日は所持金貨に入れる。期間で均等（毎分）は、その期間だけ採掘に上乗せする（金鉱の `MinePlan` に一時的な区間を足す。債券化率もかかる）。
- 債券：§4.2 と同じく上限までは資源がつき、上限を超える分は金貨に入れる（ユーザ通貨の余りと同じ。債券化率の強制などはかけない）。
- ユーザ通貨：指定日に、その日に発生したロットとして入れる。期限・余りの扱いは通貨の定義に従う。
- **通貨の設定からの初期値**（月の収入の＋差分）：

  | 行 | 量 | 通貨 | いつ・どう |
  |---|---|---|---|
  | 各ユーザ通貨 | 差分 × その月の各通貨の発生額 ÷ B | そのユーザ通貨 | 即時・一括 |
  | 残り | 差分 − 上の合計 | 金貨（うち債券化率 r の分は債券） | 即時・一括 |

  つまり「B が少し多かった月」として、自由予算の内訳と同じ割合で配る。採掘の毎分配分にはしない（その月の採掘がすでに進んでいるため）※Q5

- 予約した分（指定日・期間）は、放置計算のティックで期日が来たときに入れる（§8.2）。予約中の分は記録の詳細に「予定」として表示し、取り消せる。

### 7.1 要件

| ID | 要件 |
|---|---|
| ADJ-01 | 記録から推測した**手元にあるお金**（§7.2）を表示する |
| ADJ-02 | 実際の手元の額を入力すると、誤差（実際 − 推測）を表示する。誤差を直接 ＋／− で入力してもよい |
| ADJ-03 | ＋誤差は §4.2（債券 → おまかせ交換）、−誤差は §4.3（金貨 → 債券）で解消する |
| ADJ-04 | 調整を保存すると、その時点の実際の額が次の推測の起点になる |
| ADJ-05 | 初回（起点がない）は、入力した額を起点として保存するだけで、通貨は動かさない |
| ADJ-06 | 確定前に解消の内訳をプレビューする（§4.2 RC-04） |

### 7.2 手元のお金の推測

```
推測 ＝ 起点（前回の誤差調整で入力した実際の額）
      ＋ 起点より後の 月の収入（ベース＋差分）＋ 臨時の収入
      − 起点より後の 支出（普通の支出・サブスク・ほしい物の購入額）
```

- 対象は**自由予算の財布**。固定費・予定貯金は B に含まれないので数えない。
- 月の収入は、記録した月だけでなく、当月まで未記録の月もベース（B）で数える（記録を忘れても推測が大きくずれないように）。
- 貯金（追加・引出）を推測に含めるかは Q9。

### 8.2 放置計算（[idle.ts](../src/game/idle.ts)）

- ティックの順序「金鉱（債券化含む）→ ユーザ通貨の発生・期限 → 街の1ティック」の **金鉱の前** に「期日が来た `ScheduledGrant` を入れる」を足す。期日はティック境界に揃えないが、入る順番は時刻順で決定的にする。
- 期間で均等（毎分）の金貨は `MinePlan` の区間として扱い、`changePoints` に開始・終了を加える。

### 8.3 編集・削除

- 収入・誤差調整・サブスク／ほしい物の差分を編集したら、新旧の差を同じルールで解消する（増えた分は §4.2、減った分は §4.3）。削除は全額を逆向きに解消する。
- 予約中で未実行の `ScheduledGrant` は、編集・削除で取り消す。実行済みの分は通貨で戻す。
- 資源・建物は戻さない（RC-14）。そのため、＋と−を繰り返すと資源が増える。債券に入れ直した分に資源がつくのは needs-based-exchange.md §6.3 と同じ扱いだが、−側は手数料（RC-12）と見込み貯金に加わらないことで抑える※Q8

| `POST /api/incomes` | 月の収入（1件または一括）・臨時の収入の記録。振り分けと autoExchange を受け付ける |
| `POST /api/incomes/quote` | 記録前の振り分け・解消・おまかせ交換のプレビュー |

| `POST /api/adjustments`（`/quote`） | 誤差調整の記録（とプレビュー） |

### 8.5 画面（SCR-02 の改訂）

- タブを **収入 / 支出 / 誤差調整 / 履歴** にする（貯金の置き場は Q1）。
- 収入：上段に未記録の月の行（`7月の月収 [60,000] 円 [保存]`…`[一括保存]`）。行を開くと差分の振り分け（§5.3）と「おまかせで資源を買う」。下段に臨時の収入のフォーム。
- 支出：上段にサブスクとほしい物の行（ベース・差分・[保存]・[一括保存]）、下段に普通の支出のフォーム（現行の購入フォーム）。
- 誤差調整：推測の額と内訳（起点・収入・支出）、実際の額の入力、誤差と解消のプレビュー。
- 履歴：収入・支出・誤差調整を日付順に並べ、解消の内訳（債券・おまかせ・金貨）を表示する。

### 8.6 銀貨の報酬

- 月の収入・臨時の収入：1件につき購入と同じ 50S（1日の上限 300S は共通）。月の収入の報酬は `income:<monthKey>` で1回だけ（一括保存で複数月を入れても月ごと）※Q10
- サブスクの支払い・ほしい物の購入：購入と同じ。
- 誤差調整：報酬なし（誤差を出すほど得にならないように）。

## 10. 受入テスト（追加案）

| ID | 内容 |
|---|---|
| AT-040 | 未記録の月が当月まで並び、ベースが B になる。保存した月は並ばなくなる。同じ月は2件記録できない |
| AT-041 | 差分0の月の収入では通貨が動かない |
| AT-042 | 月の収入の＋差分の初期の振り分けが、その月の各ユーザ通貨の発生額 ÷ B の割合になる |
| AT-043 | 振り分けの「指定日」「期間で均等」が、期日のティックで入り、7日分を1回で計算しても1時間ごとに計算しても一致する |
| AT-044 | ＋差分：債券が上限に達するまで債券に入り（資源つき）、残りがおまかせ交換される。見込み貯金に加わるのはおまかせ交換の分だけ |
| AT-045 | −差分：未回収 → 所持金貨 → 債券の順で減り、債券の分に手数料がかかる |
| AT-046 | サブスクの未記録の支払いが並び、登録額のまま保存すると精算しない。請求額が安いと＋差分、高いと−差分で解消される |
| AT-047 | ほしい物を価格より安く買うと、余った積立金貨が債券 → おまかせ交換に回り、像に残らない |
| AT-048 | 手元のお金の推測 ＝ 起点 ＋ 収入 − 支出。初回の誤差調整では通貨が動かない |
| AT-049 | 記録を編集・削除すると、差分の増減が同じルールで解消され、資源・建物は減らない |

## 11. 確認したいこと

| # | 論点 | 本書の仮の決め方 |
|---|---|---|
| Q1 | 貯金（追加・引出）の記録はどこに置くか。3種類のどれかに含めるか、別に残すか | 技術Lvの根拠なので、独立した「貯金」タブとして残す（3種類の外） |
| Q2 | 月の収入のベースに「その月に有効だった B」を使うか（予算の変更履歴を持つか） | 変更履歴を持たず、今の B を使う。過去の月はベースを手で直す |
| Q3 | 月の収入の−差分（月収が B より少ない）の扱い | §4.3（金貨 → 債券）。採掘量は変えない |
| Q4 | 過去の月・過去の日付の収入も、記録した時点で通貨に入れてよいか | 入れる（支出と違い、受け取ったお金を後から使えるようにする） |
| Q5 | 「通貨の設定をデフォルトに」の意味。B の内訳（ユーザ通貨の発生額の割合）で配る、で合っているか。即時でなく、その通貨の発生ルールの日付に合わせて配るべきか | B の内訳の割合・即時（§5.3） |
| Q6 | ほしい物の−差分（価格より高い）を、ユーザ通貨も使う通常の精算順にするか、金貨 → 債券だけにするか | 金貨 → 債券だけ（差分の解消を3種類で統一） |
| Q7 | ＋差分のおまかせ交換に手数料（5S）をかけるか | かける。銀貨が足りないときは手数料なし |
| Q8 | −差分で債券を使ったときに手数料（10%、上限50S）をかけるか。誤差調整にもかけるか | かける（購入と同じ。＋−の繰り返しで資源を増やす抜け道を抑える） |
| Q9 | 手元のお金の推測に、貯金（追加・引出）を含めるか | 含めない（貯金は B の外＝予定貯金から出すことが多いため）。含める設定を設けるかは別途 |
| Q10 | 収入の記録に銀貨の報酬を出すか | 出す（購入と同じ 50S。月の収入は月ごとに1回） |
